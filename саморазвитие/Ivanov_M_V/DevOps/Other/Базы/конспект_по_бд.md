## 1. Таксономия: Выбираем оружие под задачу

> **Главный вопрос:** Что важнее — целостность (консистентность) или скорость (доступность)?

### 1.1. Реляционные базы данных (SQL)

| Характеристика | Описание |
|:---|:---|
| **Представители** | `PostgreSQL`, `MySQL`, `Oracle`, `Microsoft SQL Server` |
| **Когда нужны** | Платежи, финансы, системы бронирования, инвентаризация |
| **Философия** | Жесткая схема. Данные связаны внешними ключами (Foreign Keys) |
| **Масштабирование** | Вертикальное (мощнее железо) — предпочтительно. Горизонтальное (шардирование) — сложно |

```sql
-- Пример строгой схемы
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    balance DECIMAL(15,2) DEFAULT 0 CHECK (balance >= 0)
);
```

## 1.3. CAP-теорема (Золотое правило)
```text
      Consistency (C)
         / \
        /   \
       /     \
  CP  /       \  AP
     /         \
    /           \
   /   Partition \
  /   Tolerance   \
 /     (P)         \
/___________________\
  Availability (A)
```
- **CP-системы (SQL):** Жертвуют доступностью ради консистентности. `PostgreSQL`, `MongoDB` (по умолчанию).

- **AP-системы (NoSQL):** Жертвуют консистентностью ради доступности. `Cassandra`, `DynamoDB`.

- **CA-системы:** Не существуют в распределенном мире (отказ сети неизбежен).

## 2. Глоссарий: Расшифровка терминов
## 2.1. ACID

```sql
-- Атомарность: Все или ничего
BEGIN;
    UPDATE accounts SET balance = balance - 100 WHERE user_id = 1;
    UPDATE accounts SET balance = balance + 100 WHERE user_id = 2;
COMMIT; -- Если вторая операция упадет, первая откатится
```

| Буква | Расшифровка | Смысл |
|:---|:---|:---|
| **A** | **A**tomicity | Транзакция либо выполняется целиком, либо не выполняется вообще |
| **C** | **C**onsistency | Данные всегда остаются в валидном состоянии (ограничения, внешние ключи) |
| **I** | **I**solation | Параллельные транзакции не влияют друг на друга |
| **D** | **D**urability | Зафиксированные данные сохраняются даже при падении сервера |

## 2.2. WAL (Write-Ahead Log)
```bash
# Путь к WAL в PostgreSQL
$PGDATA/pg_wal/  # или pg_xlog в старых версиях

# Посмотреть текущий LSN (Log Sequence Number)
psql -c "SELECT pg_current_wal_lsn();"
```
**Алгоритм:**

1. Запись операции в WAL (синхронно, с fsync).
2. Подтверждение клиенту "OK".
3. Отложенная запись в таблицы (фоновый процесс).

**Почему это важно:** Если сервер упал, при старте БД "прокатывает" WAL заново, восстанавливая состояние до последней зафиксированной транзакции.

## 2.3. Репликация: Асинхронная vs Синхронная

# Сравнение в таблице
| Параметр          | Асинхронная                      | Синхронная                      |
|:------------------|:---------------------------------|:--------------------------------|
| Скорость записи   | Высокая                          | Низкая (ждет подтверждения)     |
| Риск потери данных| RPO > 0 (может потерять секунды) | RPO = 0 (все подтверждено)      |
| Задержка          | Минимальная                      | Зависит от сети до реплики      |
| Простой при сбое  | Есть риск Split-Brain            | Master блокируется при падении реплики |

## 2.4. RPO и RTO (SLA-метрики)

| Метрика | Расшифровка | Пример |
|:---|:---|:---|
| **RPO** | **R**ecovery **P**oint **O**bjective | Сколько данных мы можем потерять. Если бекап раз в сутки — RPO = 24 часа |
| **RTO** | **R**ecovery **T**ime **O**bjective | Сколько времени у нас есть на восстановление. RTO = 1 час — бизнес ждет не больше часа |

```bash
# Пример расчета
Бекап: каждые 6 часов = RPO = 6 часов
Время развертывания из бекапа: 45 минут = RTO = 45 минут
```

## 2.5. RAID для БД

| Уровень RAID | Описание | Применение для БД |
|:---|:---|:---|
| **RAID 0** | Чередование (Striping) | ❌ Нет отказоустойчивости |
| **RAID 1** | Зеркалирование (Mirroring) | ✅ Хорош, но медленный на запись |
| **RAID 5** | Чередование с четностью | ❌ **НЕ ИСПОЛЬЗОВАТЬ** (проблема *write hole*) |
| **RAID 10** | Зеркало + Чередование | ✅ **РЕКОМЕНДУЕТСЯ** (скорость + надежность) |
| **RAID 6** | Двойная четность | ✅ Для архивов, если важна надежность |

## 3. Patroni — Мозг кластера

**Что это:** Программа-агент на Python, которая автоматизирует управление PostgreSQL-кластером.

```text
      etcd/Consul/ZooKeeper (Хранилище состояния)
               |
        +------+------+
        |      |      |
     Patroni  Patroni  Patroni
     (Master) (Replica)(Replica)
        |      |      |
     PostgreSQL PostgreSQL PostgreSQL
```

## 3.2. Ключевые функции

```yaml
# Конфиг patroni.yml (фрагмент)
scope: my-cluster
namespace: /service/
name: postgresql-node1

restapi:
  listen: 0.0.0.0:8008
  connect_address: 192.168.1.10:8008

etcd:
  hosts: 192.168.1.100:2379,192.168.1.101:2379

postgresql:
  listen: 0.0.0.0:5432
  connect_address: 192.168.1.10:5432
  data_dir: /var/lib/postgresql/data
  pgpass: /tmp/pgpass
```

**Что делает Patroni:**

1. **Мониторинг** — проверяет здоровье БД каждые N секунд.
2. **Выборы лидера** — при падении мастера поднимает самую актуальную реплику.
3. **Фейловер** — автоматическое переключение с RTO < 60 секунд.
4. **Синхронизация конфигов** — все ноды знают о друг друге через etcd.

```bash
# Команды управления
patronictl list my-cluster   # Показать состояние кластера
patronictl failover          # Принудительное переключение мастера
patronictl reinit            # Переинициализация реплики
```

## 4. БД в Kubernetes: Мифы и реальность

> *Мой вердикт:* БД в K8s — ОК для DEV/QA и маленьких проектов. Для высоконагруженного PROD — выносите на отдельные VM или Bare Metal.

## 4.1. Аргументы "ПРОТИВ"
### 4.1.1. Эфемерность

```yaml
# Решается StatefulSet + PVC, но ценой производительности
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
spec:
  serviceName: postgres
  replicas: 1
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: fast-ssd   # Сетевой диск медленнее локального
      resources:
        requests:
          storage: 100Gi
```

**Проблема:** При переезде пода сетевой диск (EBS/CEPH) показывает на 30-50% меньше IOPS, чем локальный NVMe.

### 4.1.2. Производительность (Ядро и память)

```bash
# БД нужно:
# 1. Transparent Huge Pages (THP)
echo 'always' > /sys/kernel/mm/transparent_hugepage/enabled

# 2. Эксклюзивный доступ к CPU (K8s CPU Manager)
# Настройка в kubelet:
--cpu-manager-policy=static
--reserved-cpus=0-1
```

**Проблема:** В K8s сложно гарантировать, что под получит изолированное ядро и память без `swap`.

### 4.1.3. OOM Killer

```yaml
# Жесткие границы памяти (обязательно!)
resources:
  requests:
    memory: "8Gi"
    cpu: "4"
  limits:
    memory: "8Gi"   # 🔑 Должен быть равен requests!
    cpu: "6"        # CPU можно давать с запасом
```

**Что произойдет:** Если не выставить `limits = requests` для памяти, планировщик может на одну ноду положить несколько БД-подов. При пике нагрузки Linux убьет тот, у которого `oom_score` выше.

### 4.1.4. Сетевая задержка

```bash
# Тест сетевой задержки в K8s
kubectl run -it --rm busybox --image=busybox -- ping postgres-service

# Результат: ~0.5-1.5 мс дополнительно из-за CNI (Calico/Flannel/Cilium)
# Для высоконагруженной БД (>10k TPS) это катастрофа
```

## 4.2. Компромиссный подход

| Окружение | Решение |
|:---|:---|
| **Dev/Test** | БД в K8s (StatefulSet + Operator типа Zalando Postgres Operator) |
| **Prod (малый трафик)** | БД в K8s с локальными SSD (hostPath) + жесткие лимиты |
| **Prod (высокая нагрузка)** | Вынесенная БД на VM / Bare Metal, K8s подключается через Service типа ExternalName |

```yaml
# Подключение K8s к внешней БД
apiVersion: v1
kind: Service
metadata:
  name: external-postgres
spec:
  type: ExternalName
  externalName: postgres.vm-prod.internal
```

## 5. Runbook: Пошаговый план при ошибке в БД

> Протокол "Снизу вверх" — от железа к логике.

### Этап 1: Системный уровень (Диск и память)

```bash
# 1. Проверить место на диске (и inode!)
df -h  && df -i

# 2. Проверить, не уперся ли диск в IOPS
iostat -x 1 10
# Смотрим:
#   %util  > 100%  — диск умер
#   await  > 20ms  — диск не справляется

# 3. Проверить своп (swap)
free -g
swapon --show  # Должен быть пустой вывод!

# Если есть swap — БД будет тормозить
swapoff -a  # Временно отключаем (только если БД уже упала)
```

### Этап 2: Уровень БД (PostgreSQL/MySQL)

#### 2.1. Активные соединения
```sql
-- PostgreSQL
SELECT 
    pid,
    usename,
    application_name,
    client_addr,
    state,
    query_start,
    query
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY query_start;

-- Если соединений > max_connections * 0.8 — тревога!
-- Причина: приложение не закрывает коннекты (сломан пул)
```

#### 2.2. Блокировки (Locks)
```sql
-- PostgreSQL: найти все блокировки
SELECT 
    blocked.pid AS blocked_pid,
    blocked.query AS blocked_query,
    blocking.pid AS blocking_pid,
    blocking.query AS blocking_query
FROM pg_stat_activity AS blocked
JOIN pg_locks AS blocked_locks ON blocked.pid = blocked_locks.pid
JOIN pg_locks AS blocking_locks ON blocked_locks.locktype = blocking_locks.locktype
    AND blocked_locks.database IS NOT DISTINCT FROM blocking_locks.database
    AND blocked_locks.relation IS NOT DISTINCT FROM blocking_locks.relation
    AND blocked_locks.page IS NOT DISTINCT FROM blocking_locks.page
    AND blocked_locks.tuple IS NOT DISTINCT FROM blocking_locks.tuple
    AND blocked_locks.virtualxid IS NOT DISTINCT FROM blocking_locks.virtualxid
    AND blocked_locks.transactionid IS NOT DISTINCT FROM blocking_locks.transactionid
    AND blocked_locks.classid IS NOT DISTINCT FROM blocking_locks.classid
    AND blocked_locks.objid IS NOT DISTINCT FROM blocking_locks.objid
    AND blocked_locks.objsubid IS NOT DISTINCT FROM blocking_locks.objsubid
    AND blocked_locks.pid != blocking_locks.pid
JOIN pg_stat_activity AS blocking ON blocking.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;

-- Убить блокирующую транзакцию (если уверены!)
SELECT pg_terminate_backend(<blocking_pid>);
```

#### 2.3. Медленные запросы

```sql
-- PostgreSQL: запросы дольше 5 минут
SELECT 
    pid,
    now() - pg_stat_activity.query_start AS duration,
    query
FROM pg_stat_activity
WHERE 
    state = 'active' 
    AND (now() - pg_stat_activity.query_start) > interval '5 minutes'
ORDER BY duration DESC;
```

#### 2.4. Настройка логирования (должна быть включена!)
```sql
-- Включить логирование медленных запросов
-- В postgresql.conf:
-- log_min_duration_statement = '1s'
-- log_line_prefix = '%t [%p]: [%l-1] user=%u,db=%d,app=%a,client=%h '
```

### Этап 3: Проверка бекапов

```bash
# PostgreSQL: проверить последний бекап
ls -la /backup/base/ | tail -5

# Проверить, что архивы WAL идут в S3
aws s3 ls s3://my-backup-bucket/wal/ --recursive | tail -10

# Если архивы не копируются — RPO = ∞ (катастрофа)
```

### Этап 4: Восстановление (если БД упала

```bash
# 1. Поднять реплику в мастер (через Patroni)
patronictl failover my-cluster

# 2. Если Patroni нет — поднять из бекапа
pg_basebackup -D /var/lib/postgresql/data -R -P -Fp -Xs -h <replica_host> -p 5432

# 3. Восстановление Point-in-Time (PITR)
# Настройка recovery.conf:
# restore_command = 'aws s3 cp s3://my-bucket/wal/%f %p'
# recovery_target_time = '2026-08-29 14:00:00'
```
