## 0. Идея

У тебя есть приложение, которое работает локально.
Ты хочешь показать его миру → нужен выход в интернет.

На этом этапе важно понять одну вещь, которая пройдёт красной нитью через весь документ: **сложность инфраструктуры не проектируется заранее — она нарастает как ответ на конкретную боль**. Пока пользователь один (ты сам), тебе не нужны балансировщики, реплики и Kubernetes. Всё это появится позже — и только тогда, когда без этого станет больно.

## 1. MVP (Minimum Viable Product)

> «Я — стартапер, девопс, сисадмин и продакт в одном лице»

Цель этапа — как можно быстрее и дешевле сделать так, чтобы приложение открывалось в интернете по адресу вида `https://myapp.com`.

**Действия:**
- Аренда **VPS** (виртуального сервера)
- Покупка **домена** и настройка **DNS**
- Развертывание приложения (голый сервер / Docker)
- Настройка **TLS** (SSL-сертификат)
- Установка **Nginx** как веб-сервера и прокси

**Результат:** приложение доступно в интернете.

### Проблемы этапа {#проблемы-этапа-1}

| Проблема | Почему возникает |
|----------|------------------|
| «Работает у меня на ноуте, а на сервере — нет» | Разные версии ОС, библиотек, переменных окружения. Решается контейнеризацией ([Docker](#tech-docker)). |
| Приложение слушает `localhost:3000`, снаружи недоступно | Нет веб-сервера/прокси и фаервол закрыт. Решается [Nginx](#tech-nginx) + открытием портов 80/443. |
| Браузер ругается «Not secure» / «Небезопасно» | Нет HTTPS. Решается [TLS-сертификатом](#tech-tls). |
| Сайт открывается по IP, но не по домену | Не настроены [DNS](#tech-dns)-записи или не «прожились» (не пропагировались). |
| Сервер перезагрузился — приложение не поднялось | Процесс запущен вручную. Решается [systemd](#tech-systemd) (см. этап 2). |
| Пароли и ключи лежат прямо в коде | Утечка при первой же публикации репозитория. Позже решается [Vault](#tech-vault). |

### Технологии этапа {#технологии-этапа-1}

<a id="tech-vps"></a>
#### VPS — виртуальный сервер

**Что это.** VPS (Virtual Private Server) — это «кусок» физического сервера в дата-центре, который арендуется целиком под тебя: своя ОС, свой root-доступ, гарантированные CPU/RAM/диск. Дешевле выделенного сервера, но изолированнее и предсказуемее, чем шаред-хостинг.

**Зачем нужен.** Чтобы приложение работало 24/7 на машине с публичным IP-адресом, а не на твоём ноутбуке.

**Как получить и начать пользоваться.**
1. Регистрируешься у провайдера (Timeweb, Selectel, Yandex Cloud, Hetzner, DigitalOcean, AWS Lightsail и т.д.), выбираешь тариф (например, 2 vCPU / 4 ГБ RAM / 50 ГБ SSD) и образ ОС (обычно Ubuntu LTS).
2. Получаешь публичный IP и данные для входа. Подключаешься по SSH:
   ```bash
   ssh root@203.0.113.10
   ```
3. Первым делом — базовая гигиена сервера:
   ```bash
   adduser deploy                     # не работаем под root постоянно
   usermod -aG sudo deploy            # даём sudo
   # копируем свой SSH-ключ, отключаем вход по паролю в /etc/ssh/sshd_config:
   #   PasswordAuthentication no
   #   PermitRootLogin no
   ufw allow OpenSSH && ufw allow 80 && ufw allow 443 && ufw enable   # фаервол
   apt update && apt upgrade -y       # свежие обновления безопасности
   ```

**Главное правило:** сразу закрой лишние порты фаерволом и запрети вход по паролю — 90% взломов «свежих» VPS происходят перебором пароля root.

<a id="tech-dns"></a>
#### Домен и DNS

**Что это.** Домен — человекочитаемое имя (`myapp.com`). **DNS** (Domain Name System) — «телефонная книга интернета», которая переводит имя в IP-адрес.

**Зачем нужен.** Люди не запоминают `203.0.113.10`, они запоминают `myapp.com`. Плюс IP можно поменять, а домен останется.

**Ключевые типы записей.**
- `A` — имя → IPv4 (`myapp.com → 203.0.113.10`)
- `AAAA` — имя → IPv6
- `CNAME` — псевдоним (`www.myapp.com → myapp.com`)
- `MX` — почтовые серверы
- `TXT` — произвольный текст (верификация, SPF/DKIM для почты)
- `NS` — какие DNS-серверы отвечают за домен

**Как настроить.**
1. Покупаешь домен у регистратора (reg.ru, Namecheap, Cloudflare Registrar и т.д.).
2. В панели регистратора создаёшь `A`-запись, указывающую на IP твоего [VPS](#tech-vps).
3. Ждёшь **пропагации** (обновления кэшей) — от нескольких минут до 24–48 часов. Параметр `TTL` (Time To Live) задаёт, как долго кэшируется ответ.
4. Проверяешь:
   ```bash
   dig myapp.com +short      # должен вернуть твой IP
   nslookup myapp.com
   ```

> ⚠️ DNS — частая причина глобальных аварий. В разделе [«Историческая справка»](#️-историческая-справка-12-крупнейших-факапов-из-за-инфраструктуры) три из крупнейших сбоев 2021–2025 годов (Facebook, AWS, Cloudflare) начались именно с DNS/маршрутизации.

<a id="tech-docker"></a>
#### Docker — контейнеризация

**Что это.** Docker упаковывает приложение вместе со всеми зависимостями (библиотеки, интерпретатор, системные пакеты) в **контейнер** — изолированную, воспроизводимую единицу. «Собрал один раз — запускается одинаково везде».

**Зачем нужен.** Убивает проблему «у меня работало». Контейнер на ноутбуке разработчика и на проде идентичен.

**Базовые понятия.**
- **Образ (image)** — шаблон, из которого создаются контейнеры (как класс).
- **Контейнер (container)** — запущенный экземпляр образа (как объект).
- **Dockerfile** — рецепт сборки образа.
- **Volume** — постоянное хранилище (данные переживают пересоздание контейнера).

**Как установить и запустить.**
```bash
# установка (Ubuntu)
curl -fsSL https://get.docker.com | sh
usermod -aG docker deploy      # чтобы не писать sudo каждый раз

# минимальный Dockerfile
cat > Dockerfile <<'DOCKER'
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["gunicorn", "app.wsgi", "--bind", "0.0.0.0:8000"]
DOCKER

docker build -t myapp:1.0 .                       # собрать образ
docker run -d -p 8000:8000 --name myapp myapp:1.0 # запустить
docker ps                                         # что запущено
docker logs -f myapp                              # смотреть логи
```

Для нескольких сервисов сразу (приложение + БД + Nginx) используют **docker compose** — один YAML-файл описывает весь стек:
```yaml
services:
  web:
    build: .
    ports: ["8000:8000"]
  db:
    image: postgres:16
    volumes: ["pgdata:/var/lib/postgresql/data"]
volumes:
  pgdata:
```
```bash
docker compose up -d
```

<a id="tech-tls"></a>
#### TLS / SSL-сертификат

**Что это.** TLS (Transport Layer Security; SSL — устаревшее название) шифрует трафик между браузером и сервером. Это то, что превращает `http://` в `https://` и даёт замочек в адресной строке.

**Зачем нужен.**
- **Шифрование** — никто по пути не прочитает пароли и данные.
- **Аутентификация** — подтверждает, что ты общаешься именно с `myapp.com`, а не с подставным сервером.
- **Требование по умолчанию** — браузеры помечают HTTP-сайты как «небезопасные», многие API и стандарты (например, HTTP/2) требуют HTTPS.

**Как настроить бесплатно (Let's Encrypt + certbot).**
```bash
apt install certbot python3-certbot-nginx -y
# certbot сам получит сертификат и пропишет его в конфиг Nginx:
certbot --nginx -d myapp.com -d www.myapp.com
```
Certbot:
1. Подтверждает, что домен твой (ACME-challenge — кладёт файл, который проверяется по HTTP, или добавляет DNS-запись).
2. Получает сертификат от центра сертификации (CA) Let's Encrypt.
3. Настраивает [Nginx](#tech-nginx) на HTTPS и **автопродление** (сертификаты Let's Encrypt живут 90 дней):
   ```bash
   certbot renew --dry-run     # проверка автопродления
   ```

> ⚠️ **Забытый сертификат = авария.** Просроченный TLS-сертификат ронял сервисы у крупнейших компаний (см. историческую справку). Автопродление — обязательно.

<a id="tech-nginx"></a>
#### Nginx — веб-сервер и прокси

**Что это.** Nginx — высокопроизводительный веб-сервер, который также умеет быть **реверс-прокси** (принимает запросы снаружи и передаёт их приложению внутри), балансировщиком, кэшем и раздатчиком статики.

**Зачем нужен.**
- Приложение (Django/Node/…) слушает внутренний порт (`8000`), а наружу нельзя выставлять его напрямую — небезопасно и неэффективно.
- Nginx стоит «на входе» на портах 80/443, терминирует [TLS](#tech-tls), отдаёт статику (картинки, CSS, JS) быстро и без нагрузки на приложение, а динамику проксирует.

**Как установить и запустить.**
```bash
apt install nginx -y
systemctl enable --now nginx     # запустить и включить автостарт
systemctl status nginx
```

**Минимальный конфиг реверс-прокси** (`/etc/nginx/sites-available/myapp`):
```nginx
server {
    listen 80;
    server_name myapp.com www.myapp.com;

    location /static/ {
        alias /var/www/myapp/static/;      # статику отдаёт сам Nginx
    }

    location / {
        proxy_pass http://127.0.0.1:8000;  # динамику — приложению
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```
```bash
ln -s /etc/nginx/sites-available/myapp /etc/nginx/sites-enabled/
nginx -t                # проверить конфиг на ошибки (ОБЯЗАТЕЛЬНО перед reload)
systemctl reload nginx  # применить без разрыва соединений
```

**Что ещё умеет Nginx** (пригодится на следующих этапах): сжатие ответов (`gzip`), кэширование, ограничение частоты запросов (`limit_req` — защита от простого перебора и DDoS), балансировка нагрузки (см. [Load Balancer](#tech-loadbalancer)).

**Результат этапа 1:** приложение доступно в интернете по HTTPS, за нормальным веб-сервером.

## 2. Первые пользователи → первые боли

Появились реальные пользователи — и с ними всё, что может сломаться, начинает ломаться.

### Проблемы этапа {#проблемы-этапа-2}

| Проблема | Решение |
|----------|---------|
| Сервер упал ночью — сайт лежал 6 часов | Мониторинг + автоперезапуск ([systemd](#tech-systemd), [cron](#tech-cron), [healthcheck](#tech-healthcheck)) |
| Диск забит логами или данными | [Ротация логов](#tech-logrotate), увеличение диска, очистка |
| Нет бэкапов | Регулярный [бэкап](#tech-backup) БД и файлов, хранение **вне** сервера |
| Страшно деплоить в прод | Создаём **Dev-копию прода** — тестируем всё там |
| Приложение «течёт» по памяти и раз в день падает | Автоперезапуск + мониторинг памяти (лечим симптом, чинясь параллельно) |
| Один пользователь генерит тысячи запросов и кладёт сервис | Rate limiting в [Nginx](#tech-nginx) (`limit_req`) |
| Забыли продлить домен/сертификат — всё легло | Автопродление + напоминания в календаре/мониторинге |
| Задеплоили баг, откатиться нечем | Версионирование образов ([Docker](#tech-docker) tag), позже — CI/CD и быстрый rollback |

### Технологии этапа {#технологии-этапа-2}

<a id="tech-systemd"></a>
#### systemd — управление сервисами и автоперезапуск

**Что это.** systemd — система инициализации в большинстве Linux-дистрибутивов. Она запускает, останавливает, следит за сервисами и **перезапускает упавшие**.

**Зачем нужен.** Чтобы приложение поднималось само после падения или перезагрузки сервера — без человека в 3 часа ночи.

**Как использовать.** Создаёшь unit-файл `/etc/systemd/system/myapp.service`:
```ini
[Unit]
Description=My App
After=network.target

[Service]
User=deploy
WorkingDirectory=/var/www/myapp
ExecStart=/var/www/myapp/venv/bin/gunicorn app.wsgi --bind 127.0.0.1:8000
Restart=always            # ← ключевая строка: всегда перезапускать
RestartSec=3

[Install]
WantedBy=multi-user.target
```
```bash
systemctl daemon-reload
systemctl enable --now myapp     # запустить + автостарт при загрузке
systemctl status myapp
journalctl -u myapp -f           # логи сервиса в реальном времени
```

<a id="tech-cron"></a>
#### cron — планировщик задач

**Что это.** cron запускает команды по расписанию.

**Зачем нужен.** Регулярные задачи: бэкапы, очистка мусора, отправка отчётов, продление сертификатов, health-проверки.

**Как использовать.**
```bash
crontab -e
```
```cron
# ┌─ минута  ┌─ час  ┌─ день  ┌─ месяц  ┌─ день недели
  0 3 * * *   /opt/scripts/backup.sh          # каждый день в 03:00 — бэкап
  */5 * * * * /opt/scripts/healthcheck.sh     # каждые 5 минут — проверка
```
Формат «минута час день месяц день-недели». `*` = «любой».

<a id="tech-healthcheck"></a>
#### Healthcheck — проверка «жив ли сервис»

**Что это.** Специальный запрос (обычно к эндпоинту `/health` или `/healthz`), по ответу которого понятно, работает сервис или нет.

**Зачем нужен.** «Процесс запущен» ≠ «сервис работает». Приложение может висеть, не отвечая на запросы. Healthcheck проверяет именно ответ.

**Как сделать просто.** В приложении добавляешь эндпоинт, отдающий `200 OK`, и скрипт, который дёргает его по [cron](#tech-cron):
```bash
#!/bin/bash
if ! curl -fsS --max-time 5 http://127.0.0.1:8000/health > /dev/null; then
    systemctl restart myapp
    echo "$(date) restarted myapp" >> /var/log/healthcheck.log
fi
```
На следующих этапах healthcheck станет основой для [балансировщика](#tech-loadbalancer) (не слать трафик в мёртвый сервер) и [Kubernetes](#tech-k8s) (liveness/readiness-пробы).

<a id="tech-logrotate"></a>
#### Ротация логов (logrotate)

**Что это.** logrotate периодически архивирует, сжимает и удаляет старые логи, чтобы они не забили диск.

**Зачем нужен.** Логи растут бесконечно. Забитый под 100% диск роняет и приложение, и БД — это одна из самых частых «глупых» аварий.

**Как настроить** (`/etc/logrotate.d/myapp`):
```
/var/log/myapp/*.log {
    daily
    rotate 14          # хранить 14 архивов
    compress           # сжимать старые
    missingok
    notifempty
    copytruncate       # не разрывать файл, который пишет приложение
}
```

<a id="tech-backup"></a>
#### Бэкапы

**Что это.** Регулярные копии данных (БД, загруженные файлы, конфиги), хранящиеся **отдельно** от основного сервера.

**Зачем нужен.** Диск умирает, команда удаляется по ошибке, приходит шифровальщик-вымогатель. Без бэкапа — данные потеряны навсегда. История GitLab (см. историческую справку) — про то, как **пять** методов бэкапа оказались нерабочими одновременно.

**Правило 3-2-1:** 3 копии данных, на 2 разных носителях, 1 копия — вне площадки (offsite).

**Как сделать (пример для PostgreSQL).**
```bash
#!/bin/bash
# backup.sh — запускается по cron раз в сутки
DATE=$(date +%F)
pg_dump -U app mydb | gzip > /backups/mydb-$DATE.sql.gz
# отправляем копию во внешнее хранилище (S3-совместимое)
aws s3 cp /backups/mydb-$DATE.sql.gz s3://myapp-backups/
# удаляем локальные копии старше 7 дней
find /backups -name '*.sql.gz' -mtime +7 -delete
```

> ⚠️ **Бэкап, который ни разу не восстанавливали, — это не бэкап, а надежда.** Регулярно проверяй восстановление на тестовом сервере.

## 3. Команда растёт

Появились разработчики (несколько человек) — и в фокус выходят совместная работа над кодом, контроль доступа и учёт задач.

**Появляются:**
- Разработчики (несколько человек)
- Потребность в контроле версий → **GitHub / GitLab**
- Разграничение прав доступа (админ → полный доступ, разработчики → ограниченный)
- **Тикет-система** (Trello, Notion, YouTrack) — задачи, приоритеты, сроки

### Проблемы этапа {#проблемы-этапа-3}

| Проблема | Решение |
|----------|---------|
| Код пересылают в архивах, версии путаются | Единый репозиторий на [Git](#tech-git) |
| Двое правят один файл — правки затирают друг друга | Ветки + merge/pull request + код-ревью |
| «Кто и когда сломал прод?» — непонятно | История коммитов, `git blame`, обязательное ревью |
| У всех root-доступ ко всему | [Разграничение прав (RBAC)](#tech-rbac), принцип наименьших привилегий |
| Уволенный сотрудник сохранил доступы | Централизованное управление доступами, регулярный аудит и отзыв |
| Задачи теряются в чатах и голове | [Тикет-система](#tech-tickets) с приоритетами и статусами |
| Секреты (пароли БД, ключи) закоммичены в репозиторий | `.gitignore`, секреты вне кода, позже — [Vault](#tech-vault) |

### Технологии этапа {#технологии-этапа-3}

<a id="tech-git"></a>
#### Git и хостинг репозиториев (GitHub / GitLab)

**Что это.** **Git** — распределённая система контроля версий: хранит всю историю изменений кода, позволяет вести параллельные **ветки** и сливать их. **GitHub / GitLab / Bitbucket** — веб-платформы поверх Git с ревью, задачами и [CI/CD](#tech-cicd).

**Зачем нужен.** Совместная работа без «затирания» правок, полная история «кто/что/когда/зачем», возможность откатиться к любой прошлой версии.

**Базовый рабочий процесс.**
```bash
git clone git@github.com:team/myapp.git
git checkout -b feature/login        # своя ветка под задачу
# ...правишь код...
git add . && git commit -m "add login form"
git push origin feature/login        # отправляешь ветку
# дальше на GitHub/GitLab создаёшь Merge/Pull Request → ревью → merge в main
```

**Ключевые практики команды.**
- **Защищённая ветка `main`** — нельзя пушить напрямую, только через ревью.
- **Pull/Merge Request** — обязательный код-ревью перед вливанием.
- **Conventional commits / понятные сообщения** — чтобы история читалась.

<a id="tech-rbac"></a>
#### Разграничение прав доступа (RBAC)

**Что это.** RBAC (Role-Based Access Control) — модель, где права выдаются не человеку напрямую, а **роли** (admin, developer, viewer), а роль — человеку.

**Зачем нужен.** Чтобы разработчик не мог случайно (или намеренно) удалить прод, а стажёр — читать секреты. Основа — **принцип наименьших привилегий**: у каждого ровно столько прав, сколько нужно для работы, и ни каплей больше.

**Как применяется на практике.**
- В [Git](#tech-git)-платформе: роли Owner/Maintainer/Developer/Guest.
- На серверах: разные Linux-пользователи, `sudo` только тем, кому надо, вход по SSH-ключам.
- В облаке: IAM-политики (кто к каким ресурсам имеет доступ).
- Везде, где можно, — **2FA** (двухфакторная аутентификация).

<a id="tech-tickets"></a>
#### Тикет-системы

**Что это.** Инструменты учёта задач: Trello, Jira, YouTrack, Notion, Linear, GitLab/GitHub Issues.

**Зачем нужны.** Единый список задач с приоритетами, сроками, ответственными и статусами. «Что делаем, кто делает, в каком состоянии» — видно всем.

**Базовый порядок.** Задача заводится тикетом → попадает в бэклог → берётся в работу (обычно доска Kanban: To Do → In Progress → Review → Done) → закрывается со ссылкой на соответствующий Merge Request в [Git](#tech-git).

## 4. База данных

**Проблема:** БД и приложение на одном сервере → тормоза (конкурируют за CPU, память и диск).

**Решение:**
- Перенос БД на **отдельный сервер**
- Соединение через **приватную сеть** (VLAN / VPC)
- Nginx становится **полноценным реверс-прокси**: сжатие ответов, кэширование статики, лимит запросов с одного IP

### Проблемы этапа {#проблемы-этапа-4}

| Проблема | Решение |
|----------|---------|
| Приложение и БД дерутся за ресурсы одного сервера | Вынос БД на отдельную машину |
| БД доступна из интернета (потенциальная дыра) | [Приватная сеть](#tech-privatenet), БД слушает только внутренний интерфейс |
| Медленные запросы кладут базу | Индексы, оптимизация запросов, пул соединений |
| Статика грузит приложение | Отдаём статику через [Nginx](#tech-nginx)/кэш ([реверс-прокси](#tech-reverse)) |
| Один клиент перегружает сервис | Rate limiting в [Nginx](#tech-nginx) |
| «Потеряли» соединения к БД под нагрузкой | Пулер соединений (PgBouncer для PostgreSQL) |

### Технологии этапа {#технологии-этапа-4}

<a id="tech-privatenet"></a>
#### Приватная сеть (VLAN / VPC)

**Что это.** Изолированная внутренняя сеть, в которой общаются твои серверы. **VLAN** — на своём железе; **VPC** (Virtual Private Cloud) — в облаке. Трафик между приложением и БД идёт по приватным адресам и не выходит в интернет.

**Зачем нужна.**
- **Безопасность:** БД не имеет публичного IP — снаружи к ней вообще не подключиться.
- **Скорость и стабильность:** внутренний трафик быстрее и не платится как внешний.

**Как применяется.**
- Приложение и БД в одном VPC/подсети.
- БД слушает только приватный интерфейс (`listen_addresses = '10.0.0.5'`), фаервол пускает к порту 5432 только с адреса приложения.
- Наружу открыты лишь 80/443 у [Nginx](#tech-nginx). Всё остальное — внутри.

<a id="tech-reverse"></a>
#### Реверс-прокси

Реверс-прокси — это режим работы [Nginx](#tech-nginx), уже описанного на [этапе 1](#tech-nginx). Здесь он «дорастает» до полноценного: добавляем сжатие, кэш и лимиты.

```nginx
http {
    gzip on;                                   # сжатие ответов
    gzip_types text/plain text/css application/json application/javascript;

    # кэш статики от бэкенда
    proxy_cache_path /var/cache/nginx keys_zone=static_cache:10m;

    # лимит: не больше 10 запросов/сек с одного IP
    limit_req_zone $binary_remote_addr zone=perip:10m rate=10r/s;

    server {
        location /api/ {
            limit_req zone=perip burst=20 nodelay;
            proxy_pass http://127.0.0.1:8000;
        }
    }
}
```

## 5. Крупные клиенты → требования по надёжности

**Uptime 99.9%** = максимум **8 часов 46 минут простоя в год**. Для сравнения: 99.99% («четыре девятки») — это уже ~52 минуты в год, а 99.999% — ~5 минут. Каждая девятка стоит дорого и требует убрать все **единые точки отказа** (single point of failure).

### Что делаем:
- Добавляем **несколько серверов**
- **Балансировщик нагрузки** (Nginx / HAProxy / облачный LB)
- **Репликация БД** (Master → Replica). Если Master падает — Replica становится Master (без даунтайма)
- **Отдельный сервер для статики** (или объектное хранилище S3)
- **Собственный registry образов** (Harbor, Nexus, GitLab Registry) — чтобы не зависеть от Docker Hub

### Проблемы этапа {#проблемы-этапа-5}

| Проблема | Решение |
|----------|---------|
| Один сервер = одна точка отказа | Несколько инстансов + [балансировщик](#tech-loadbalancer) |
| Упал сервер с БД — всё легло | [Репликация](#tech-replication), автоматический failover |
| Не тянем пиковую нагрузку | Горизонтальное масштабирование (добавить серверов за LB) |
| Файлы пользователей раздуваются на локальном диске | [Объектное хранилище S3](#tech-s3) |
| Docker Hub недоступен / ввёл лимиты — деплой встал | [Собственный registry](#tech-registry) образов |
| Логи разбросаны по 10 серверам, ничего не найти | [Централизованные логи](#tech-logs) |
| Сессии пользователей «слетают» при переключении сервера | Общее хранилище сессий (Redis), а не память конкретного инстанса |
| Данные между master и replica расходятся | Понимание синхронной/асинхронной репликации, мониторинг лага |

### Технологии этапа {#технологии-этапа-5}

<a id="tech-loadbalancer"></a>
#### Балансировщик нагрузки (Load Balancer)

**Что это.** Компонент, который распределяет входящие запросы между несколькими одинаковыми серверами приложения. Варианты: [Nginx](#tech-nginx), HAProxy, облачный LB (AWS ELB/ALB, Yandex LB), или L4-балансировщик.

**Зачем нужен.**
- **Масштабирование:** нагрузка делится между инстансами.
- **Отказоустойчивость:** LB опрашивает [healthcheck](#tech-healthcheck) и не шлёт трафик в упавший сервер.
- **Бесшовные деплои:** можно по одному выводить серверы из-под нагрузки, обновлять, возвращать.

**Как настроить (Nginx, простой round-robin).**
```nginx
upstream backend {
    least_conn;                      # слать туда, где меньше активных соединений
    server 10.0.0.11:8000 max_fails=3 fail_timeout=15s;
    server 10.0.0.12:8000 max_fails=3 fail_timeout=15s;
    server 10.0.0.13:8000 backup;    # резервный
}
server {
    listen 443 ssl;
    location / { proxy_pass http://backend; }
}
```

**Важно:** приложение должно быть **stateless** — не хранить пользовательские сессии в своей памяти, иначе при переключении сервера пользователя «разлогинит». Сессии выносят в общий Redis/БД.

<a id="tech-replication"></a>
#### Репликация БД (Master → Replica)

**Что это.** Копирование данных с основного сервера БД (**master/primary**) на один или несколько **реплик (replica/standby)** в реальном времени.

**Зачем нужна.**
- **Отказоустойчивость:** упал master — реплика становится новым master (**failover**).
- **Масштабирование чтения:** тяжёлые SELECT-ы можно направлять на реплики, разгружая master.
- **Бэкапы без нагрузки:** снимаем [бэкап](#tech-backup) с реплики.

**Синхронная vs асинхронная.**
- **Синхронная** — master ждёт подтверждения от реплики → нет потери данных, но выше задержка.
- **Асинхронная** — master не ждёт → быстрее, но при падении можно потерять последние транзакции (**лаг репликации**).

**Как включить (PostgreSQL, упрощённо).**
```conf
# на master (postgresql.conf)
wal_level = replica
max_wal_senders = 10
# в pg_hba.conf разрешаем реплике подключаться
```
```bash
# на реплике — снять базовую копию с master и запуститься как standby
pg_basebackup -h 10.0.0.5 -U repl -D /var/lib/postgresql/data -R
```
Автоматический failover обычно делают надстройки: **Patroni**, **repmgr**, **pgpool**.

<a id="tech-s3"></a>
#### Объектное хранилище (S3)

**Что это.** S3 (Simple Storage Service) и его совместимые аналоги (MinIO, Yandex Object Storage, Ceph) — хранилище **объектов** (файлов) с доступом по HTTP-API. Не файловая система и не БД — «бесконечный» склад для картинок, видео, бэкапов, статики.

**Зачем нужно.**
- Локальный диск не резиновый и не отказоустойчив.
- Объектное хранилище масштабируется «бесконечно», реплицируется само, отдаёт файлы напрямую (часто через [CDN](#tech-cdn)).

**Базовые понятия:** **bucket** (корзина/контейнер), **object** (файл + метаданные), **key** (путь-имя объекта).

**Как пользоваться (S3-совместимое API).**
```bash
aws s3 mb s3://myapp-media                  # создать bucket
aws s3 cp avatar.png s3://myapp-media/users/ # загрузить
aws s3 ls s3://myapp-media/users/            # список
```
Приложение хранит в БД только **ключ** объекта, а сам файл — в бакете.

<a id="tech-registry"></a>
#### Собственный registry образов

**Что это.** Приватный реестр [Docker](#tech-docker)-образов: Harbor, Nexus, GitLab Container Registry, AWS ECR. Аналог Docker Hub, но свой.

**Зачем нужен.**
- **Независимость:** публичный Docker Hub может быть недоступен или ввести лимиты на скачивание — и деплой встанет.
- **Безопасность:** приватные образы не утекают наружу; часто есть встроенное **сканирование на уязвимости**.
- **Скорость:** образы качаются из своей сети.

**Как пользоваться.**
```bash
docker login registry.mycompany.com
docker tag myapp:1.0 registry.mycompany.com/team/myapp:1.0
docker push registry.mycompany.com/team/myapp:1.0
```

<a id="tech-logs"></a>
#### Централизованные логи (ELK / Loki / Graylog)

**Что это.** Система сбора логов со всех серверов в одно место с поиском и визуализацией. Популярные стеки: **ELK/Elastic** (Elasticsearch + Logstash + Kibana), **Grafana Loki** (+ Promtail + Grafana), **Graylog**.

**Зачем нужна.** Когда серверов десятки, `ssh` на каждый и `grep` по логам не работает. Нужен единый поиск: «покажи все ошибки 500 за последний час по всем инстансам».

**Как устроено (на примере Loki).**
1. **Агент** (Promtail/Fluent Bit/Vector) на каждом сервере читает логи и шлёт их в центральное хранилище.
2. **Хранилище** (Loki/Elasticsearch) индексирует и хранит.
3. **UI** (Grafana/Kibana) — поиск, фильтры, дашборды, алерты.

**Хорошая практика — структурные логи** (JSON) с полями `level`, `request_id`, `user_id`. Тогда логи можно фильтровать и связывать с [трассировкой](#-трассировка-подробно).

### Логи централизованно:
Graylog, Grafana Loki, ELK-стек — см. подробно [выше](#tech-logs).

## 6. Постмортемы и автоматизация

**Инциденты фиксируются**, разбираются в **постмортемах**, чтобы не повторялись.

> **Постмортем** (post-mortem) — разбор инцидента после его устранения: что произошло, почему, как чинили, что сделать, чтобы не повторилось. Ключевой принцип — **blameless** (без поиска виноватых): ищем сломанный процесс, а не «плохого человека». Практически все крупные аварии из [исторической справки](#️-историческая-справка-12-крупнейших-факапов-из-за-инфраструктуры) сопровождались публичными постмортемами.

**Ручное управление — невозможно** → внедряем оркестрацию и «инфраструктуру как код».

### Проблемы этапа {#проблемы-этапа-6}

| Проблема | Решение |
|----------|---------|
| Руками катить на десятки серверов — долго и с ошибками | Оркестрация ([Kubernetes](#tech-k8s)/[Swarm](#tech-swarm)) + [CI/CD](#tech-cicd) |
| «На проде конфиг не такой, как на staging» (дрейф конфигурации) | [Инфраструктура как код](#tech-terraform) (Terraform/Ansible) |
| Секреты раскиданы по .env и головам | [Vault](#tech-vault), секреты по сервисам |
| Сервис упал, а узнали от пользователей | [Мониторинг](#-мониторинг-подробно) + алерты |
| «Тормозит где-то в цепочке из 15 сервисов» — где? | [Трассировка](#-трассировка-подробно) (Jaeger/Tempo) |
| Одинаковые инциденты повторяются | Постмортемы + автоматизация устранения |
| Задеплоили — и всё легло, откат вручную полчаса | Быстрый rollback, canary/blue-green деплой |
| Нагрузка скачет: то простой, то перегруз | Автомасштабирование (HPA в [Kubernetes](#tech-k8s)) |

### CI/CD эволюционирует:

```text
Тесты → Линтеры → Безопасность → Сборка → Пуш в registry → Деплой на Dev → E2E-тесты → Деплой на Staging → Ручная проверка → Деплой на Prod
```

### Технологии этапа {#технологии-этапа-6}

<a id="tech-k8s"></a>
#### Kubernetes — оркестрация контейнеров

**Что это.** Kubernetes (K8s) — система, которая управляет [контейнерами](#tech-docker) на кластере серверов: сама запускает, перезапускает упавшие, масштабирует, распределяет по нодам, обновляет без простоя.

**Зачем нужен.** Когда контейнеров сотни и серверов десятки, вручную это не удержать. K8s превращает «стадо серверов» в один управляемый пул: ты описываешь **желаемое состояние**, а он его поддерживает.

**Ключевые объекты.**
- **Pod** — минимальная единица (один или несколько тесно связанных контейнеров).
- **Deployment** — управляет набором одинаковых подов (сколько реплик держать, как обновлять).
- **Service** — стабильная внутренняя точка входа к подам (встроенная балансировка).
- **Ingress** — вход снаружи (по сути управляемый [Nginx](#tech-nginx)/прокси).
- **ConfigMap / Secret** — конфиги и секреты.
- **HPA** (Horizontal Pod Autoscaler) — автомасштабирование по нагрузке.

**Пример манифеста и запуска.**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: myapp }
spec:
  replicas: 3
  selector: { matchLabels: { app: myapp } }
  template:
    metadata: { labels: { app: myapp } }
    spec:
      containers:
        - name: myapp
          image: registry.mycompany.com/team/myapp:1.0
          ports: [{ containerPort: 8000 }]
          livenessProbe:                 # ← healthcheck из этапа 2
            httpGet: { path: /health, port: 8000 }
          readinessProbe:
            httpGet: { path: /ready, port: 8000 }
```
```bash
kubectl apply -f deployment.yaml     # применить желаемое состояние
kubectl get pods                     # что запущено
kubectl rollout undo deployment/myapp # мгновенный откат
kubectl logs -f deploy/myapp
```

<a id="tech-swarm"></a>
#### Docker Swarm

**Что это.** Более простой оркестратор от [Docker](#tech-docker). Тот же принцип, что у [Kubernetes](#tech-k8s), но заметно легче в освоении и беднее по возможностям.

**Зачем нужен.** Когда K8s — избыточен (небольшая команда, десяток сервисов), а один сервер уже мал.

```bash
docker swarm init
docker service create --replicas 3 --name myapp registry.mycompany.com/team/myapp:1.0
docker service scale myapp=5
```

<a id="tech-ansible"></a>
#### Ansible

**Что это.** Инструмент управления конфигурацией серверов: описываешь в YAML-«плейбуках», что должно быть на серверах (пакеты, файлы, сервисы), и Ansible приводит их к этому состоянию по SSH. Агент на серверах не нужен.

**Зачем нужен.** Настроить 1 сервер вручную — норм. Настроить 50 одинаково и повторяемо — только код. Ansible **идемпотентен**: повторный запуск ничего не ломает, только доводит до нужного состояния.

```yaml
# playbook.yml
- hosts: web
  become: true
  tasks:
    - name: install nginx
      apt: { name: nginx, state: present, update_cache: true }
    - name: nginx running
      service: { name: nginx, state: started, enabled: true }
```
```bash
ansible-playbook -i inventory.ini playbook.yml
```

<a id="tech-cicd"></a>
#### CI/CD-конвейер

**Что это.** **CI** (Continuous Integration) — на каждый пуш автоматически прогоняются тесты/линтеры/сборка. **CD** (Continuous Delivery/Deployment) — прошедший проверки код автоматически доставляется на окружения. Инструменты: GitLab CI, GitHub Actions, Jenkins, Argo CD.

**Зачем нужен.** Убирает «ручной деплой ночью». Каждое изменение проходит один и тот же путь проверок — предсказуемо и быстро, с возможностью отката.

**Пример (GitLab CI, `.gitlab-ci.yml`).**
```yaml
stages: [test, build, deploy]

test:
  stage: test
  script:
    - pip install -r requirements.txt
    - flake8 .          # линтер
    - pytest            # тесты

build:
  stage: build
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA   # в свой registry

deploy_prod:
  stage: deploy
  when: manual          # прод — только по кнопке
  script:
    - kubectl set image deployment/myapp myapp=$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
```

**Стратегии безопасного деплоя.**
- **Blue-Green:** держим два окружения; переключаем трафик на новое, старое — мгновенный откат.
- **Canary:** выкатываем на 5% трафика, смотрим метрики, потом на 100%.
- **Rolling update:** обновляем поды по одному (по умолчанию в [K8s](#tech-k8s)).

<a id="tech-terraform"></a>
#### Terraform — инфраструктура как код

**Что это.** Terraform описывает **саму инфраструктуру** (серверы, сети, балансировщики, БД в облаке) декларативным кодом. Ты пишешь, что должно быть, — Terraform создаёт/меняет это через API провайдера.

**Зачем нужен.** Инфраструктура становится **воспроизводимой** и версионируемой в [Git](#tech-git). Можно поднять идентичный staging одной командой, увидеть в ревью, что именно меняется, и не иметь «дрейфа» между окружениями.

```hcl
resource "yandex_compute_instance" "web" {
  count = 3
  name  = "web-${count.index}"
  resources { cores = 2; memory = 4 }
  boot_disk { initialize_params { image_id = var.ubuntu_image } }
}
```
```bash
terraform plan     # показать, ЧТО изменится (обязательно смотреть!)
terraform apply    # применить
```

> Разница с [Ansible](#tech-ansible): Terraform создаёт **инфраструктуру** (что существует), Ansible настраивает **то, что внутри** серверов. Часто используют вместе.

<a id="tech-vault"></a>
#### HashiCorp Vault — управление секретами

**Что это.** Централизованное хранилище секретов (пароли БД, API-ключи, TLS-ключи) с шифрованием, аудитом доступа и **динамическими** секретами (выдаёт временные креды, которые сами протухают).

**Зачем нужен.** Секреты в коде/`.env` рано или поздно утекают. Vault держит их в одном защищённом месте, выдаёт по запросу нужному сервису, ведёт журнал «кто что брал», умеет **ротацию** (регулярную смену).

**Принцип «каждому сервису — свои секреты»:** сервис A не может прочитать секреты сервиса B. Утечка одного сервиса не компрометирует всё.

```bash
vault kv put secret/myapp/db password=s3cr3t
vault kv get secret/myapp/db
# приложение получает секрет по токену с ограниченными правами, а не хранит его в образе
```

### 🔍 Мониторинг (подробно)

**Зачем.** «Нельзя управлять тем, что не измеряешь». Мониторинг отвечает на два вопроса: **работает ли система сейчас** и **что сломается скоро**. Без него об авариях узнают от пользователей в соцсетях.

**Три столпа наблюдаемости (observability).**
1. **Метрики** — числа во времени (CPU, память, RPS, задержки, ошибки). Инструменты: **Prometheus**, VictoriaMetrics.
2. **Логи** — текстовые события ([централизованные логи](#tech-logs), этап 5).
3. **Трейсы** — путь запроса через сервисы (см. [Трассировка](#-трассировка-подробно)).

**Prometheus + Grafana + Alertmanager — как это работает.**
- **Prometheus** периодически «скребёт» (pull) метрики с эндпоинтов `/metrics` твоих сервисов и хранит их как временные ряды.
- **Grafana** рисует дашборды по этим данным.
- **Alertmanager** шлёт уведомления (Telegram, Slack, PagerDuty, почта), когда метрика вышла за порог.

```bash
# приложение отдаёт метрики на /metrics (клиентские библиотеки есть для всех языков)
# prometheus.yml
scrape_configs:
  - job_name: myapp
    static_configs:
      - targets: ['10.0.0.11:8000', '10.0.0.12:8000']
```
```yaml
# правило алерта: >5% ошибок 5xx за 5 минут
- alert: HighErrorRate
  expr: rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m]) > 0.05
  for: 5m
  labels: { severity: critical }
```

**Что мониторить — не только «железо».**
- **Системные метрики:** CPU, RAM, диск (обязательно — заполнение!), сеть.
- **Прикладные (SRE «золотые сигналы»):** **Latency** (задержка), **Traffic** (нагрузка), **Errors** (ошибки), **Saturation** (насыщенность ресурсов).
- **Бизнес-метрики:** заказы в минуту, регистрации, платежи. Падение бизнес-метрики при «зелёном» железе — сигнал о скрытой поломке.

**SLI / SLO / SLA — язык надёжности.**
- **SLI** (Indicator) — что измеряем (например, доля успешных запросов).
- **SLO** (Objective) — внутренняя цель (99.9% успешных за месяц).
- **SLA** (Agreement) — обещание клиенту с санкциями за нарушение.
- **Error budget** (бюджет ошибок) — сколько «даунтайма» ещё можно потратить, не нарушив SLO. Кончился бюджет — замораживаем фичи, чиним надёжность.

**Дежурства (on-call).** Инженеры по очереди «на телефоне». Алерт → уведомление (PagerDuty/Opsgenie) → реакция по **runbook** (пошаговой инструкции на этот тип инцидента). Важно бороться с **alert fatigue** — усталостью от ложных алертов: алертить только на то, что реально требует действия человека.

### 🛡️ Безопасность (подробно)

**Принцип.** Безопасность — не «фича в конце», а свойство на всех слоях (**defense in depth** — эшелонированная оборона): если пробьют один слой, есть следующий.

**Основные направления.**

1. **Сетевой периметр.** Фаервол, закрытые лишние порты, БД в [приватной сети](#tech-privatenet), [WAF](#tech-waf) перед приложением, защита от DDoS (Cloudflare, облачные scrubbing-центры).

2. **Управление доступом.** [RBAC](#tech-rbac) и наименьшие привилегии, обязательная **2FA/MFA**, SSO, отзыв доступов при увольнении, регулярный **аудит** «кто к чему имеет доступ».

3. **Секреты.** [Vault](#tech-vault), никаких паролей в коде, регулярная **ротация** ключей, разные секреты для dev/prod.

4. **Шифрование.**
   - **In transit** (в пути) — [TLS](#tech-tls) везде, включая внутренний трафик (mTLS в service mesh).
   - **At rest** (на диске) — шифрование дисков и бэкапов.

5. **Управление уязвимостями.**
   - **Патч-менеджмент:** своевременное обновление ОС и библиотек. *Утечка Equifax (147 млн человек) произошла из-за непропатченной известной уязвимости — см. историческую справку.*
   - **Сканирование образов** [Docker](#tech-docker) (Trivy, Grype) и зависимостей (SCA).
   - **SAST/DAST** — статический и динамический анализ кода на уязвимости, встроенный в [CI/CD](#tech-cicd).

6. **Практики разработки.** Валидация ввода (защита от SQL-инъекций и XSS), подготовленные запросы к БД, принцип «не доверяй пользовательскому вводу», код-ревью с фокусом на безопасность.

7. **Обнаружение и реакция.** **IDS/IPS** (системы обнаружения/предотвращения вторжений), **SIEM** (сбор и корреляция событий безопасности), план реагирования на инциденты (**IR-plan**), регулярные **пентесты** (см. [этап 8](#8-новые-роли-и-задачи)).

8. **Модель Zero Trust.** «Никому не доверяем по умолчанию» — каждый запрос аутентифицируется и авторизуется, даже внутри периметра. Внутренняя сеть больше не считается «безопасной сама по себе».

**OWASP Top 10** — базовый чек-лист самых частых веб-уязвимостей (инъекции, сломанная аутентификация, небезопасная конфигурация и т.д.); с него стоит начинать любой аудит.

### 🧵 Трассировка (подробно)

**Проблема.** В микросервисной архитектуре один запрос пользователя проходит через десятки сервисов (API-gateway → auth → catalog → pricing → payment → …). Если «где-то тормозит» или «падает 500» — по логам одного сервиса не понять, **где именно** и **почему**.

**Что это.** **Распределённая трассировка** (distributed tracing) прослеживает **весь путь** одного запроса между сервисами. Инструменты: **Jaeger**, **Grafana Tempo**, Zipkin; стандарт сбора данных — **OpenTelemetry**.

**Ключевые понятия.**
- **Trace** — полный путь одного запроса через все сервисы.
- **Span** — одна операция внутри трейса (вызов сервиса, запрос к БД) со своим временем начала/конца.
- **Trace ID** — общий идентификатор, который «прокидывается» через все сервисы (в заголовках), связывая спаны в один трейс.

**Как это выглядит.** В UI Jaeger/Tempo видна «водопадная» диаграмма: сразу понятно, что из 800 мс запроса 650 мс ушло на один медленный SQL в сервисе pricing. Это и есть узкое место.

**Как внедряют.**
1. Подключают SDK **OpenTelemetry** в каждый сервис.
2. Настраивают **контекст-пропагацию** — передачу `trace_id` в заголовках между сервисами.
3. Экспортируют спаны в коллектор → в Jaeger/Tempo.
4. **Связка трёх столпов:** по одному `trace_id` можно прыгнуть из трейса в [логи](#tech-logs) и [метрики](#-мониторинг-подробно) этого же запроса. Это и называется **observability** (наблюдаемость).

```python
# пример: ручной span поверх авто-инструментации
from opentelemetry import trace
tracer = trace.get_tracer(__name__)
with tracer.start_as_current_span("charge_payment"):
    charge(order)     # длительность и статус этой операции попадут в трейс
```

## 7. Платформенная команда

> Команд много, каждая строит инфру по-своему → хаос.

**Платформенная команда** не делает продукт — она создаёт **инструменты для разработчиков** (это подход **Platform Engineering**). Её «клиент» — не пользователь продукта, а разработчики других команд. Цель — чтобы продуктовым командам было легко делать правильно и трудно — неправильно.

### Проблемы этапа {#проблемы-этапа-7}

| Проблема | Решение |
|----------|---------|
| Каждая команда изобретает свой CI/CD, мониторинг, деплой | Единая внутренняя платформа (IDP) с готовыми шаблонами |
| Знания о деплое — в голове одного «гуру» | Самообслуживание: разработчик всё делает сам через портал |
| Разнобой в стандартах → сложно поддерживать | [Общие стандарты](#общие-стандарты) для всех |
| Команды мешают друг другу на общих ресурсах | [Разделение окружений](#разделение-окружений) и квоты |
| Падение одного продукта роняет соседний | [Отдельные кластеры](#отдельные-кластеры-под-продукты) под критичные продукты |
| Высокая **когнитивная нагрузка** на разработчика | Платформа прячет сложность инфраструктуры за простым интерфейсом |

### 🔧 Что делает платформенная команда

#### ВНУТРЕННЯЯ ПЛАТФОРМА РАЗРАБОТЧИКА (IDP)

**IDP** (Internal Developer Platform) — «одна кнопка», за которой скрыта вся сложность:
- **ОДНА КНОПКА** — единый портал самообслуживания (например, на базе Backstage).
- **Шаблон сервиса** — новый сервис создаётся из готового шаблона (репозиторий, Dockerfile, манифесты [K8s](#tech-k8s) — уже настроены).
- **[CI/CD](#tech-cicd) настроен** «из коробки».
- **Мониторинг, логи «из коробки»** — [метрики](#-мониторинг-подробно), [логи](#tech-logs) и [трейсы](#-трассировка-подробно) подключаются автоматически.

#### ОБЩИЕ СТАНДАРТЫ
- **[CI/CD](#tech-cicd)** — единый конвейер для всех.
- **Общие окружения** — единые инструменты для всех команд; так удобнее компании в целом.
- «Golden path» — рекомендованный, проторённый путь: делаешь как принято — всё работает само.

#### РАЗДЕЛЕНИЕ ОКРУЖЕНИЙ
- **dev** — окружение разработки.
- **staging** — максимально похоже на прод, финальная проверка.
- **preprod** — предпродакшн, «репетиция» релиза на данных, близких к боевым.
- **prod** — боевое окружение.

Разделение нужно, чтобы эксперименты в dev **никогда** не влияли на боевых пользователей.

#### ОТДЕЛЬНЫЕ КЛАСТЕРЫ ПОД ПРОДУКТЫ
- **КЛАСТЕР ПРОДУКТА А** (критичный)
- **КЛАСТЕР ПРОДУКТА Б** (критичный)
- Dev/Staging могут жить в общем кластере с **квотами** (лимитами ресурсов на команду), чтобы одна команда не «съела» весь кластер.

## 8. Новые роли и задачи

С ростом системы одному «девопсу-на-всё» уже не справиться — появляются специализированные роли.

| Роль | Задачи |
|------|--------|
| **DBA** (Database Administrator) | Администрирование БД, [репликация](#tech-replication), оптимизация запросов и индексов, шардирование, планирование ёмкости |
| **QA-инженеры** | Разработка тестов для пайплайнов, автоматизация, нагрузочное и E2E-тестирование |
| **ИБ / InfoSec** | Пентесты, [WAF](#tech-waf), 2FA, аудит доступов, управление секретами, проверки безопасности в [CI/CD](#tech-cicd) |
| **SRE** (Site Reliability Engineer) | Надёжность, [SLO/error budget](#-мониторинг-подробно), дежурства, автоматизация эксплуатации |
| **Platform Engineer** | Внутренняя [платформа](#7-платформенная-команда) для разработчиков |
| **Data Engineer** | Пайплайны данных, хранилища, аналитика |
| **FinOps** | Контроль и оптимизация облачных расходов |

### Проблемы этапа {#проблемы-этапа-8}

| Проблема | Решение |
|----------|---------|
| Атаки на веб (SQL-инъекции, XSS, боты) | [WAF](#tech-waf), валидация ввода, rate limiting |
| «Размытая» ответственность за надёжность | Роль SRE, чёткие [SLO](#-мониторинг-подробно) |
| БД стала узким местом и «чёрным ящиком» | Выделенный DBA |
| Облачный счёт растёт непонятно почему | FinOps, теги ресурсов, бюджеты и алерты на траты |
| Ручное тестирование не успевает за релизами | Автотесты в [CI/CD](#tech-cicd), выделенные QA |

### Технологии и роли этапа

<a id="tech-waf"></a>
#### WAF — межсетевой экран уровня приложений

**Что это.** WAF (Web Application Firewall) — фильтр **HTTP-трафика** перед приложением. Анализирует запросы и блокирует вредоносные паттерны: SQL-инъекции, XSS, попытки обхода, подозрительные боты. Варианты: Cloudflare WAF, AWS WAF, ModSecurity (self-hosted).

**Зачем нужен.** Обычный фаервол работает на уровне портов/IP и не понимает содержимое HTTP. WAF «читает» запросы и отсекает атаки на уровне приложения ещё до того, как они дойдут до кода.

**Как работает.**
- **Негативная модель** (сигнатуры) — блокирует известные вредоносные паттерны (например, набор правил **OWASP Core Rule Set**).
- **Позитивная модель** — разрешает только заведомо валидные запросы.
- Часто совмещён с **rate limiting**, **bot management** и **anti-DDoS**.

```nginx
# пример с ModSecurity перед Nginx-бэкендом
modsecurity on;
modsecurity_rules_file /etc/nginx/modsec/main.conf;   # подключаем OWASP CRS
```

> ⚠️ WAF — важный слой, но **не замена** безопасному коду. Это часть [эшелонированной обороны](#️-безопасность-подробно), а не серебряная пуля.

## 9. Юридическое регулирование

### Почему законы диктуют архитектуру

Когда продукт работает с данными людей и деньгами, **закон становится техническим требованием**. «Где физически лежат данные», «как быстро мы можем удалить пользователя», «где хранятся логи с персональными данными» — это уже не только инженерные, но и юридические вопросы. Несоблюдение → **огромные штрафы** (по GDPR — до €20 млн или 4% мирового годового оборота), блокировки и потеря доверия.

Ключевые рамки:
- **Персональные данные:** 152-ФЗ (РФ), GDPR (ЕС), CCPA/CPRA (Калифорния), LGPD (Бразилия), PIPL (Китай) и др.
- **Платежи:** PCI DSS (стандарт индустрии платёжных карт).
- **Отраслевые:** HIPAA (медицина, США), GLBA (финансы, США).
- **ИИ:** EU AI Act (регулирование систем искусственного интеллекта в ЕС).

### 20+ требований, которые должны соблюдать компании

Это универсальный чек-лист; конкретные формулировки различаются по странам (см. ниже).

1. **Правовое основание обработки.** Обрабатывать персональные данные только при наличии законного основания (согласие, договор, законный интерес и т.д.).
2. **Явное согласие.** Получать понятное, добровольное, отзываемое согласие; для детей — согласие родителей.
3. **Минимизация данных.** Собирать только то, что реально нужно для цели.
4. **Ограничение цели.** Использовать данные только для тех целей, ради которых собрали.
5. **Ограничение хранения.** Не хранить данные дольше необходимого; иметь политику удаления.
6. **Прозрачность.** Понятная политика конфиденциальности: что, зачем и как собирается.
7. **Право на доступ.** По запросу выдать пользователю все его данные.
8. **Право на исправление.** Позволить исправить неверные данные.
9. **Право на удаление («право на забвение»).** Удалить данные по запросу (технически — включая бэкапы и реплики!).
10. **Право на переносимость.** Отдать данные в машиночитаемом формате для переноса к конкурету.
11. **Право на возражение / отказ (opt-out).** Возможность отказаться от обработки, особенно для рекламы/профилирования.
12. **Уведомление об утечках.** Сообщать регулятору (часто в течение 72 часов) и пострадавшим при утечке.
13. **Security by design & by default.** Закладывать защиту данных на этапе проектирования, безопасные настройки по умолчанию.
14. **Шифрование.** Шифровать данные [в пути и на диске](#️-безопасность-подробно).
15. **Контроль доступа и аудит.** [RBAC](#tech-rbac), журналирование доступа к персональным данным.
16. **DPIA / оценка воздействия.** Проводить оценку рисков для рискованной обработки.
17. **DPO / ответственный за данные.** Назначить ответственного (Data Protection Officer), где это требуется.
18. **Договоры с подрядчиками (DPA).** С каждым обработчиком данных (облако, аналитика) — договор об обработке.
19. **Резидентность / локализация данных.** Хранить данные граждан в определённой юрисдикции (жёстко — в РФ и Китае).
20. **Регулирование трансграничной передачи.** Передавать данные за границу только при адекватной защите (SCC, adequacy decision).
21. **Отдельная защита особых категорий.** Здоровье, биометрия, религия, политика — усиленные требования.
22. **Соответствие PCI DSS для платежей.** Не хранить полный номер карты и CVV, токенизация, сегментация сети.
23. **Ведение реестра обработки (RoPA).** Документировать все процессы обработки персональных данных.
24. **Cookie-согласие.** Баннеры согласия на трекинг-куки (особенно в ЕС по ePrivacy).
25. **Права при автоматизированных решениях.** Право не быть объектом чисто автоматического решения без участия человека; прозрачность ИИ (EU AI Act).

### 🇷🇺 Россия

- **152-ФЗ «О персональных данных»** — базовый закон.
- **Локализация (242-ФЗ):** первичный сбор и хранение персональных данных **граждан РФ** — на серверах, физически расположенных **в России**. Это прямое архитектурное требование.
- **Уведомление Роскомнадзора** о намерении обрабатывать персональные данные; ведение реестра операторов.
- **Уведомление об утечках** в Роскомнадзор — в сжатые сроки (в течение 24 часов о факте, далее — детали).
- **Ужесточение ответственности (с 2025):** введены **оборотные штрафы** за утечки персональных данных (процент от годовой выручки при повторных/крупных нарушениях) — кратно выше прежних фиксированных сумм.
- **Требования ФСТЭК/ФСБ** к защите информационных систем персональных данных (ГИС, КИИ), сертифицированные средства защиты для ряда систем.
- **187-ФЗ о КИИ** — для объектов критической информационной инфраструктуры (энергетика, финансы, связь) — свои требования по защите и отчётности.

### 🇪🇺 Евросоюз

- **GDPR** — эталонный и самый строгий режим. Экстерриториален: действует на любую компанию, обрабатывающую данные жителей ЕС, где бы она ни находилась.
- **Штрафы:** до **€20 млн или 4% мирового годового оборота** (что больше). Крупнейший штраф — **€1,2 млрд компании Meta** (2023) за передачу данных в США.
- **Уведомление об утечке — 72 часа** регулятору.
- **DPO** обязателен для систематического мониторинга/крупных объёмов особых категорий.
- **Трансграничная передача** только при «адекватности» страны или через SCC (стандартные договорные положения) / EU-US Data Privacy Framework.
- **ePrivacy («Cookie Law»):** согласие на нестрого необходимые куки — до их установки.
- **EU AI Act** (вступает поэтапно): классификация ИИ по риску, запрет ряда практик, прозрачность и человеческий надзор для «высокорисковых» систем.
- **NIS2, DORA:** усиленные требования к кибербезопасности и операционной устойчивости (особенно финсектор).

### 🇺🇸 США

- **Нет единого федерального закона** о персональных данных — «лоскутное одеяло» из отраслевых и штатных законов (20+ штатов имеют свои законы к 2026).
- **CCPA/CPRA (Калифорния):** модель **opt-out** (по умолчанию можно, но пользователь вправе запретить продажу/передачу данных), право на доступ/удаление, «Do Not Sell My Personal Information». Штрафы — за нарушение (порядка $2 500–7 500 за инцидент/запись).
- **Отраслевые законы:** **HIPAA** (медицинские данные), **GLBA** (финансовые), **COPPA** (данные детей до 13 лет), **FERPA** (образование).
- **Уведомления об утечках** регулируются **на уровне штатов** (свои сроки и правила в каждом из 50 штатов).
- **FTC** преследует «нечестные и вводящие в заблуждение практики» как де-факто регулятор приватности на федеральном уровне.

### 🌍 Другие страны

- **🇧🇷 Бразилия — LGPD:** близка к GDPR, регулятор ANPD; штрафы до 2% выручки в Бразилии, максимум ~R$50 млн за нарушение.
- **🇨🇳 Китай — PIPL + Data Security Law + Cybersecurity Law:** очень строго. **Локализация** важных данных, обязательная **оценка безопасности** для трансграничной передачи, штрафы до **5% годового оборота**. (Прецедент: Didi оштрафован на ~$1,2 млрд.)
- **🇬🇧 Великобритания — UK GDPR** + Data Protection Act: почти калька GDPR после Brexit.
- **🇨🇦 Канада — PIPEDA** (+ Quebec Law 25): смешанная модель согласия, упор на «информированное согласие».
- **🇮🇳 Индия — DPDP Act (2023):** согласие-центричный режим; штрафы до ~₹250 крор (~$30 млн).
- **🇿🇦 ЮАР — POPIA**, **🇦🇺 Австралия — Privacy Act/APP** (порог по выручке), **🇯🇵 Япония — APPI**, **🇰🇷 Корея — PIPA**, **🇸🇬 Сингапур — PDPA**, **🇦🇪 ОАЭ / 🇸🇦 Саудовская Аравия — PDPL**.
- **💳 PCI DSS** — не закон, а стандарт индустрии, но обязателен по договору для всех, кто принимает карты, **во всём мире**: сегментация сети, запрет хранить CVV, токенизация, регулярные сканирования.

> **Вывод для архитектора:** правило «где хранить и как удалять данные» часто определяется юристами, а не инженерами. При работе на несколько юрисдикций проектируют под **самое строгое** применимое требование и закладывают **резидентность данных** (в какой стране лежат данные какого пользователя) уже на уровне архитектуры БД и [шардирования](#tech-sharding).

## 10. Мировой масштаб

> Продукт используют во всём мире → нужно, чтобы везде открывалось быстро.

Физику не обмануть: свет идёт по оптоволокну ~200 000 км/с, и запрос из Австралии на сервер в Вирджинии всегда будет медленным. Поэтому инфраструктуру **приближают к пользователю**.

### Проблемы этапа {#проблемы-этапа-10}

| Проблема | Решение |
|----------|---------|
| Пользователи на другом континенте — всё грузится медленно | [CDN](#tech-cdn) + [мульти-регион](#tech-multiregion) |
| Отказ целого дата-центра/региона | Мульти-региональный деплой, failover между регионами |
| Данные должны лежать в стране пользователя (закон) | [Шардирование по регионам](#tech-sharding), резидентность данных |
| Синхронизация БД между континентами тормозит запись | Асинхронная репликация, локальная запись + гео-репликация |
| Один регион (типа AWS us-east-1) — скрытая точка отказа | Мультирегион/мультиоблако для критичного (урок аварий 2025) |
| Растёт облачный счёт | FinOps, резервирование мощностей, гибрид |

### Технологии этапа {#технологии-этапа-10}

<a id="tech-cdn"></a>
#### CDN — сеть доставки контента

**Что это.** CDN (Content Delivery Network) — сеть кэширующих серверов по всему миру (Cloudflare, Akamai, Fastly, CloudFront). Пользователь получает статику (картинки, видео, CSS/JS, а иногда и кэш API) с ближайшего к нему узла (**edge**), а не с исходного сервера (**origin**).

**Зачем нужен.**
- **Скорость:** контент отдаётся из точки в 20 мс от пользователя, а не из-за океана.
- **Разгрузка origin:** до 90%+ запросов закрывается кэшем на edge.
- **Защита:** большинство CDN включают анти-DDoS и [WAF](#tech-waf).

**Как подключить (базово).**
1. Направляешь [DNS](#tech-dns) домена на CDN (меняешь NS или ставишь CNAME на edge).
2. Указываешь **origin** — свой [балансировщик](#tech-loadbalancer)/[S3](#tech-s3).
3. Настраиваешь правила кэширования (`Cache-Control`, TTL, что кэшировать).
```
Cache-Control: public, max-age=31536000, immutable   # для версионированной статики
```

> ⚠️ CDN — тоже точка централизации. Сбой Cloudflare 18.11.2025 положил тысячи сайтов разом (см. историческую справку).

<a id="tech-multiregion"></a>
#### Мульти-региональный деплой

**Что это.** Развёртывание приложения в нескольких географических регионах (например, EU + US + Asia), с маршрутизацией пользователя в ближайший здоровый регион (GeoDNS / Anycast).

**Зачем нужен.**
- **Отказоустойчивость:** упал регион — трафик уходит в другой (**failover**).
- **Скорость:** обработка ближе к пользователю.
- **Резидентность:** данные региона обрабатываются в этом регионе (см. [юридический раздел](#9-юридическое-регулирование)).

**Уровни устойчивости.**
- **Multi-AZ** (несколько зон доступности в одном регионе) — базовый минимум для прода.
- **Multi-Region** — защита от отказа целого региона.
- **Multi-Cloud** — защита от отказа целого провайдера (дорого и сложно, но для критичного — оправдано; урок [AWS us-east-1](#️-историческая-справка-12-крупнейших-факапов-из-за-инфраструктуры) от октября 2025).

<a id="tech-sharding"></a>
#### Геораспределённые БД и шардирование

**Проблема.** Держать одну БД, синхронную на всех континентах, невозможно без огромных задержек на запись.

**Решения.**
- **Асинхронная репликация** между регионами — быстро, но с лагом и риском конфликтов.
- **Шардирование (sharding)** — разбиение данных на части (**шарды**) по ключу. **Шардирование по региону:** данные россиян → в РФ, американцев → в США. Это одновременно и про скорость, и про **резидентность данных** (закон).
- **Распределённые SQL-БД** (CockroachDB, YugabyteDB, Google Spanner) — умеют гео-распределение «из коробки» с настройкой, где физически живёт каждая строка.

```
Пользователь RU ──▶ шард RU (БД в России)
Пользователь US ──▶ шард US (БД в США)
Глобальные справочники ──▶ реплицируются во все регионы
```

**Сложности шардирования:** запросы «через все шарды», ребалансировка при росте, транзакции между шардами. Поэтому его вводят **как можно позже** — только когда одна БД уже не тянет.

### Где размещать инфраструктуру? (с примерами компаний)

| Вариант | Плюсы | Минусы | Кто так делает (примеры) |
|---------|-------|--------|--------------------------|
| **Облако** (AWS, GCP, Azure, Yandex Cloud) | Быстрый старт, платишь по факту, лёгкое масштабирование, управляемые сервисы | Дорого на больших объёмах, зависимость от провайдера (vendor lock-in), риск сбоя региона | **Netflix** (полностью на AWS), **Airbnb**, **Lyft** (GCP), **Spotify** (мигрировал в GCP), большинство стартапов |
| **Bare Metal** (своё железо / colocation) | Полный контроль, максимум производительности, дешевле при огромном стабильном объёме, независимость | Капзатраты, нужна команда под железо и ДЦ, долгий ввод мощностей, сам отвечаешь за всё | **Stack Overflow** (знаменит работой на своём железе), крупные банки, **VK / Яндекс** (свои ДЦ), телеком-операторы |
| **Гибрид** (Hybrid) | Критичное/чувствительное — на своём железе, эластичное/пиковое — в облаке; баланс контроля и гибкости | Сложность управления двумя мирами, сетевые связки, двойная экспертиза | **Dropbox** (ушёл из AWS на своё хранилище «Magic Pocket», оставив часть в облаке), банки и госсектор, ритейл с сезонными пиками |
| **Мультиоблако** (Multi-Cloud) | Нет зависимости от одного вендора, устойчивость к отказу провайдера, торг по цене | Максимальная сложность, дороже в поддержке, «общий знаменатель» сервисов | Крупные enterprise, критичные финтех/платёжные системы |

**Отдельный тренд — «репатриация»:** некоторые компании, дорастя до огромных стабильных объёмов, **уходят из облака** обратно на своё железо ради экономии. Самый известный пример — **Dropbox**, сэкономивший сотни миллионов долларов; про это же публично писали в **37signals/Basecamp**. Мораль: «облако vs железо» — это не идеология, а расчёт под конкретный масштаб и профиль нагрузки.

## 🕰️ Историческая справка: 12 крупнейших факапов из-за инфраструктуры

История индустрии — это история аварий. Почти каждый компонент из этого документа появился потому, что где-то что-то **очень больно** сломалось. Ниже — реальные кейсы (все сопровождались публичными постмортемами).

**1. Knight Capital, 2012 — $440 млн за 45 минут.**
Торговая фирма выкатила обновление на 8 серверов, но на **один** не доехал деплой. Там ожил старый, годами «мёртвый» код, привязанный к переиспользованному флагу. Робот начал бесконтрольно слать ошибочные биржевые заявки. За ~45 минут компания потеряла ~$440 млн и фактически перестала существовать.
*Урок: контроль деплоя, отсутствие «мёртвого» кода, feature-флаги, мгновенный [rollback](#tech-cicd).*

**2. Amazon S3 (AWS), февраль 2017 — опечатка уронила пол-интернета.**
Инженер отлаживал биллинг [S3](#tech-s3) и командой хотел вывести несколько серверов — но из-за **опечатки** вывел гораздо больше, включая подсистемы метаданных. Регион us-east-1 лёг на ~4 часа, вместе с ним — Slack, Trello, Quora, Medium и тысячи сайтов. Даже статус-дашборд AWS не работал, потому что сам хостился на S3. Убытки S&P 500 оценили в ~$150 млн.
*Урок: ограничивать «радиус поражения» команд, автоматические проверки, статус-страница на **отдельной** инфраструктуре.*

**3. Facebook / Instagram / WhatsApp, октябрь 2021 — «Facebook удалил себя из интернета».**
Во время планового обслуживания магистральной сети команда случайно отключила все дата-центры от [BGP](#tech-dns). [DNS](#tech-dns)-серверы, увидев обрыв, автоматически «отозвали» свои маршруты — и Facebook исчез с карты интернета на ~6 часов. Хуже того: внутренние инструменты и **пропуска в здания** зависели от той же сети, поэтому инженеры не могли попасть внутрь ДЦ, чтобы всё починить. Потери — десятки миллионов выручки и ~$47 млрд капитализации в моменте.
*Урок: опасность жёсткой связанности (tight coupling), независимый «запасной» канал управления (out-of-band).*

**4. GitLab, январь 2017 — удалили прод-базу, а все 5 бэкапов не сработали.**
Уставший инженер, борясь со спамом и репликацией, случайно выполнил удаление каталога **основной** БД (перепутал сервер). Попытались восстановиться — и выяснили, что **все пять** методов бэкапа [не работали](#tech-backup): один — на несовместимой версии PostgreSQL, другой писал в никуда, и т.д. Потеряли ~6 часов данных (~5000 проектов). GitLab вёл восстановление в прямом эфире на YouTube.
*Урок: бэкап без регулярной **проверки восстановления** — это иллюзия. Защита от удаления прода.*

**5. CrowdStrike, июль 2024 — крупнейший IT-сбой в истории.**
Обновление конфигурации антивируса Falcon (Channel File 291) содержало логическую ошибку (чтение за границами памяти). Поскольку код работал на **уровне ядра** Windows, ~**8,5 млн** машин ушли в «синий экран» и бут-луп по всему миру. Встали аэропорты (отменено >5000 рейсов), банки, больницы, службы 911. Многие машины пришлось чинить **вручную**, физически. Оценка ущерба Fortune-500 — ~$5,4 млрд.
*Урок: поэтапный (canary) раскат даже «конфигов», а не сразу на всех; тестирование обновлений; опасность единого софта в ядре у всех.*

**6. AWS us-east-1, октябрь 2025 — гонка в DNS уронила полмира на 15 часов.**
Скрытая **race condition** в автоматике управления [DNS](#tech-dns) для DynamoDB привела к тому, что записи о том, где искать базу, были удалены. Отказ каскадом пошёл по зависимым сервисам (EC2, сеть, 100+ сервисов). ~15 часов лежали Snapchat, Fortnite, Roblox, Coinbase, Ring, McDonald's, даже налоговая Британии. Оценка страховых убытков — до ~$581 млн.
*Урок: даже мультирегиональные сервисы падали, потому что глобальный **control plane** (IAM, Route 53) завязан на us-east-1 — единая скрытая точка отказа.*

**7. Cloudflare, ноябрь 2025 — файл, который «удвоился».**
Изменение прав в БД привело к тому, что служебный «feature file» системы Bot Management **удвоился в размере**. Софт на всех узлах сети не смог его обработать и начал падать с ошибками 500. Полмира (X, ChatGPT, Spotify, Canva) не открывалось несколько часов.
*Урок: валидация конфигов по размеру/схеме, защита от «раздувания», canary-раскат внутренних файлов. Внутренняя ошибка обходит внешнюю защиту.*

**8. Fastly (CDN), июнь 2021 — одна настройка одного клиента.**
Один клиент изменил свою конфигурацию — и это активировало скрытый баг в [CDN](#tech-cdn). За минуты по всему миру отвалились Reddit, Spotify, The Guardian, Amazon, портал gov.uk. Глобальный сбой длился ~час.
*Урок: латентные баги + мгновенная глобальная раскатка = глобальная авария. Нужна поэтапность и быстрый откат.*

**9. British Airways, май 2017 — сбой питания в дата-центре.**
Проблема с электропитанием в ДЦ под Лондоном (по официальной версии — неконтролируемый скачок напряжения при восстановлении питания) вывела из строя системы. ~75 000 пассажиров застряли, отменены сотни рейсов в разгар выходных. Ущерб — оценочно £58–80 млн.
*Урок: резервирование питания и **корректный** failover; отработанные процедуры восстановления, а не только «есть второй ДЦ».*

**10. TSB Bank, апрель 2018 — миграция, которую не отрепетировали.**
Банк переносил 1,3 млрд записей на новую платформу. Миграцию недотестировали — и после переключения **1,9 млн** клиентов не могли войти в онлайн-банк, видели чужие счета, не проходили платежи. Проблемы тянулись месяцами. Итог: ~£330 млн затрат и штраф регуляторов (~£48,65 млн).
*Урок: репетиция миграций на копии прода, план отката, поэтапное переключение, а не «большой взрыв».*

**11. Equifax, 2017 — непропатченная уязвимость на 147 млн человек.**
Кредитное бюро не установило вовремя патч к **известной** уязвимости в Apache Struts (CVE-2017-5638). Через неё злоумышленники украли персональные данные ~147 млн человек (номера соцстрахования и др.). Урегулирование обошлось до ~$700 млн.
*Урок: [патч-менеджмент](#️-безопасность-подробно) и управление уязвимостями — не «когда-нибудь», а процесс. Сегментация и мониторинг доступа к чувствительным данным.*

**12. Cloudflare, июль 2019 — одно регулярное выражение положило сеть.**
В правило [WAF](#tech-waf) попало «прожорливое» регулярное выражение с катастрофическим бэктрекингом. Оно взвинтило CPU до 100% на всех серверах Cloudflare разом — глобальный сбой на ~30 минут.
*Урок: тестировать правила на производительность, ограничивать ресурсы, раскатывать поэтапно даже «правила фильтрации».*

**Общий знаменатель всех 12 историй:**
- Почти всегда триггер — **человеческая ошибка или рутинное изменение**, а не хакеры.
- Убивает не сама ошибка, а **каскад** и **жёсткая связанность** компонентов.
- Спасают: поэтапная раскатка (canary), быстрый откат, проверенные бэкапы, «радиус поражения», независимый канал управления и честные постмортемы.

## 🧠 Итог

> **Каждый компонент появился на конкретную боль.**
> Сложность никто не проектировал — **она выросла сама.**

Пройдём весь путь одним взглядом: начали с [приложения на ноутбуке](#0-идея) → арендовали [VPS](#tech-vps), купили [домен](#tech-dns) и повесили [TLS](#tech-tls) за [Nginx](#tech-nginx) → получили первых пользователей и первую боль, ответив на неё [автоперезапуском](#tech-systemd), [ротацией логов](#tech-logrotate) и [бэкапами](#tech-backup) → выросла команда, пришли [Git](#tech-git) и [разграничение прав](#tech-rbac) → БД задохнулась и переехала в [приватную сеть](#tech-privatenet) → крупные клиенты потребовали надёжности, и появились [балансировщики](#tech-loadbalancer), [репликация](#tech-replication) и [объектное хранилище](#tech-s3) → ручное управление стало невозможным, и его заменили [Kubernetes](#tech-k8s), [CI/CD](#tech-cicd), [IaC](#tech-terraform), [мониторинг](#-мониторинг-подробно), [безопасность](#️-безопасность-подробно) и [трассировка](#-трассировка-подробно) → хаос множества команд собрала [платформенная команда](#7-платформенная-команда) → закон стал архитектурным требованием ([юридический раздел](#9-юридическое-регулирование)) → и, наконец, продукт вышел на [мировой масштаб](#10-мировой-масштаб) с [CDN](#tech-cdn), [мультирегионом](#tech-multiregion) и [шардированием](#tech-sharding).

**Что здесь по-настоящему трудно** (и где ломаются даже гиганты — см. [историческую справку](#️-историческая-справка-12-крупнейших-факапов-из-за-инфраструктуры)):

- **Состояние и данные — самое сложное.** Stateless-приложения масштабировать легко; БД, [репликация](#tech-replication), [шардирование](#tech-sharding) и **консистентность данных между регионами** — это то, на чём спотыкаются. Данные нельзя «просто перезапустить», как упавший под.
- **Бэкапы и восстановление.** Бэкап, который ни разу не восстанавливали, не существует. История [GitLab](#️-историческая-справка-12-крупнейших-факапов-из-за-инфраструктуры) — вечное напоминание.
- **Каскадные отказы и связанность.** Самые громкие аварии (Facebook, AWS, Cloudflare) — это когда мелкая ошибка через жёсткие зависимости роняет всё. Проектировать надо **изоляцию** и **радиус поражения**.
- **Скрытые единые точки отказа.** Один регион, один провайдер, один служебный файл, один DNS. Их находят, как правило, уже во время аварии.
- **Раскатка изменений.** Мгновенный глобальный деплой = мгновенная глобальная авария. Canary/blue-green, поэтапность и быстрый откат — не роскошь.
- **Безопасность и патч-менеджмент** — процесс, а не разовая задача ([Equifax](#️-историческая-справка-12-крупнейших-факапов-из-за-инфраструктуры)).
- **Люди и процессы.** Триггер большинства аварий — рутинное изменение уставшего инженера. Поэтому важны blameless-постмортемы, runbooks, автоматизация опасных операций и здоровые дежурства.

**Главная мысль.** Инфраструктура — это не набор модных технологий, а **последовательность ответов на боль**, где каждый ответ добавляет и пользу, и новую сложность. Хороший инженер вводит компонент **тогда, когда без него уже больно**, — не раньше (преждевременная сложность так же опасна, как её нехватка) и не позже.

**Архитектор инфраструктуры** — тот, кто держит в голове всю эту карту целиком: видит, какая боль наступит следующей, где прячутся единые точки отказа и какой минимальной сложностью можно закрыть максимум рисков.
