## 👥 Роли и команды в DevOps

| Роль | Описание |
| ------ | ---------- |
| **Разработчики (Dev)** | Пишут код, добавляют фичи, исправляют баги. |
| **Системные администраторы (Ops)** | Поддерживают серверы, следят за доступностью сервисов. |
| **DevOps-инженер** | Объединяет навыки разработки и эксплуатации, автоматизирует процессы, настраивает CI/CD, обеспечивает надежность инфраструктуры. |
| **SRE (Site Reliability Engineering)** | Применяет DevOps-подходы для обеспечения высокой доступности и масштабируемости сервисов. |

### Специализации DevOps

| Тип | Описание |
| ----- | ---------- |
| **Команда DevOps** | В больших компаниях может быть целая команда: одни сопровождают разработчиков, другие пишут автоматизацию. |
| **DevOps "на один продукт"** | В одной команде с разработчиками, глубокое погружение в один сервис. |
| **DevOps под конкретную задачу** | Узкие специализации: команда мониторинга, команда Kubernetes, команда CI/CD. |

## 🐧 Linux для DevOps

### Зачем DevOps знать Linux

1. **Основная ОС для серверов**
   - Почти все хостинги и облака предлагают Linux (Ubuntu, CentOS, Debian, Alpine).
   - Windows Server — меньшая часть рынка.

2. **Быстрый доступ к логам и настройкам**
   - Когда что-то падает, DevOps заходит по SSH, смотрит логи, проверяет нагрузку.

3. **Среда для большинства инструментов**
   - CI/CD, контейнеры, конфигурационные менеджеры работают в Linux-окружении.

### Ключевые навыки Linux

| Навык | Описание |
| ------- | ---------- |
| **Командная строка (CLI)** | Базовые команды: `ls`, `cd`, `mkdir`, `rm`, `cp`, `mv`, `sudo`. |
| **Фильтрация и поиск** | `grep`, `find`, `xargs`, `awk`, `sed` для работы с логами и данными. |
| **Структура каталогов** | `/etc` — конфиги, `/var/log` — логи, `/home` — пользователи. |
| **Права доступа** | `chmod`, `chown`, `umask`, управление пользователями и группами. |
| **Управление сервисами** | `systemctl`, `journalctl`, создание `.service`-юнитов. |
| **Процессы** | `ps`, `top`, `htop` для мониторинга CPU и RAM. |
| **Пакетные менеджеры** | `apt` (Ubuntu/Debian), `yum/dnf` (CentOS/RHEL). |
| **Логи** | `/var/log/syslog`, `/var/log/nginx/error.log`. |
| **Скриптинг** | Bash для автоматизации, Python для сложных задач. |
| **SELinux** | Понимание контекстов и разрешений (особенно в госструктурах). |
| **Firewall** | `iptables`, `ufw`, `nftables` для фильтрации трафика. |

### Популярные дистрибутивы

| Дистрибутив | Пакетный менеджер | Где используется |
| ------------- | ------------------- | ------------------ |
| **Debian/Ubuntu** | APT | Стартапы, облачные серверы |
| **CentOS/AlmaLinux/RHEL** | YUM/DNF | Крупные компании, госсектор |
| **Alpine** | APK | Легковесные Docker-образы |

## 🌐 Сети для DevOps

### Зачем DevOps знать сети

- Настройка доступа к сервисам (порты, доменные имена).
- Контейнеры и виртуалки требуют IP-адресов и маршрутов.
- Работа с DNS-записями.
- Настройка Nginx и SSL-сертификатов.

### Базовые компоненты сети

| Компонент | Описание |
| ----------- | ---------- |
| **IP-адрес** | У каждого сервера, контейнера, пода есть свой IP. |
| **Порты (TCP/UDP)** | HTTP:80, HTTPS:443, SSH:22. Если порт закрыт — доступ извне невозможен. |
| **Маршрутизация** | Как пакеты доходят от клиента к серверу через шлюзы и NAT. |
| **DNS** | Переводит доменные имена в IP-адреса. Утилиты: `nslookup`, `dig`. |
| **HTTP/HTTPS** | Протоколы передачи веб-страниц. HTTPS требует SSL-сертификат. |
| **SSL-сертификаты** | Let's Encrypt, Comodo. Настройка автоматического обновления. |
| **Файрволы** | `iptables`, `nftables` для фильтрации трафика. |
| **SSH, VPN** | Безопасный доступ к серверам и внутренним сетям. |
| **OSI модель** | Понимание уровней: физический, канальный, сетевой, транспортный, сеансовый, представления, прикладной. |

### Сетевые утилиты

| Утилита | Назначение |
| --------- | ------------ |
| `ping` | Проверка доступности хоста. |
| `traceroute` / `tracepath` | Отображение маршрута пакетов. |
| `telnet` / `nc` | Проверка доступности порта. |
| `nslookup` / `dig` | Проверка DNS-записей. |

### Взаимодействие с облаками

| Компонент | Описание |
| ----------- | ---------- |
| **Облачные сети** | VPC, подсети, роут-тейблы, NAT-шлюзы. |
| **Балансировщики** | L4/L7 Load Balancer, K8s Ingress, AWS ALB. |
| **Облачные провайдеры** | Yandex Cloud, VK Cloud, Sber Cloud, AWS. |

### Пример решения сетевой проблемы

**Ситуация:** Сервис "orders" не может достучаться до базы PostgreSQL.

1. `ping` сервера базы — проверка доступности.
2. `nslookup orders-db.mycompany.lan` — проверка DNS.
3. `telnet ip_db 5432` — проверка порта.
4. Зайти на сервер, проверить `iptables -L`.
5. Добавить правило: `iptables -A INPUT -p tcp --dport 5432 -j ACCEPT`.
6. Проверить, что всё работает.
7. Закрепить в Terraform/Ansible для автоматизации.

## 📦 Docker: Контейнеризация

### Проблема, которую решает Docker

> "У меня локально всё работает, а на сервере всё упало!"

Docker упаковывает приложение и все зависимости в **контейнер**, который работает одинаково везде.

### Анатомия Docker

| Компонент | Описание |
| ----------- | ---------- |
| **Образ (Image)** | "Шаблон" с библиотеками, кодом и настройками. Неизменяемый. |
| **Контейнер (Container)** | Запущенный экземпляр образа. Живущая копия. |
| **Docker Engine** | Сервис, управляющий контейнерами (запуск, остановка). |
| **Registry** | Хранилище образов (Docker Hub). |

```bash
Docker Image (неизменяемый шаблон)
├── Слой OS
├── Зависимости
└── Код приложения
↓ build
Docker Containers (запущенные экземпляры)
├── Контейнер 1 🚀
├── Контейнер 2 🚀
└── Контейнер 3 🚀
```

### Что дает Docker DevOps

| Преимущество | Описание |
| -------------- | ---------- |
| **Единая среда** | Одинаковое окружение на всех машинах. |
| **Легкое масштабирование** | Запуск нескольких контейнеров из одного образа. |
| **Быстрый деплой** | Сборка образа, загрузка в registry, запуск за секунды. |

**Основные команды:**

- `docker run` — запуск контейнера.
- `docker ps` — список контейнеров.
- `docker build` — сборка образа из Dockerfile.
- `docker stop / rm` — остановка/удаление контейнера.

### Docker Compose

> Описание нескольких сервисов (приложение + база + кеш) в одном файле.  
> Запуск всей среды одной командой.

### Docker Workflow

```bash
Dockerfile → Build → Registry → Run
```

## ☸️ Kubernetes: Оркестрация

### Проблема, которую решает Kubernetes

- Много контейнеров (десятки, сотни).
- Нужно автоматически перезапускать упавшие контейнеры.
- Масштабирование при росте трафика.

### Как устроен Kubernetes

| Компонент | Описание |
| ----------- | ---------- |
| **Кластер** | Несколько машин (узлов), объединенных в одну систему. |
| **Поды (Pods)** | Минимальная единица. Содержит один или несколько контейнеров. |
| **Deployment** | Определяет количество реплик (копий) подов. Обеспечивает автовосстановление. |
| **Service** | Единый IP/имя для доступа к подам. Балансирует трафик. |
| **ConfigMap** | Хранит конфигурационные данные (несекретные). |
| **Secrets** | Хранит чувствительные данные (пароли, ключи). |

### Docker + Kubernetes: Мощное комбо

| Инструмент | Роль |
|------------|------|
| **Docker** | Упаковывает приложение в контейнер. |
| **Kubernetes** | Управляет множеством контейнеров, обеспечивая надежность и масштабируемость. |

> **Роль DevOps:** Настроить Docker и Kubernetes так, чтобы сервис мог быстро развернуться, восстанавливаться и не падать под наплывом пользователей.

## 🔄 CI/CD: Continuous Integration / Continuous Delivery

### Что такое Continuous Integration (CI)

**CI** – "непрерывная интеграция":

- Когда любой новый код (commit, merge) разработчика автоматически проверяется.
- Система (Jenkins, GitLab CI, GitHub Actions) скачивает свежий код, собирает, запускает тесты.

**Зачем это?**

- Выявлять проблемы "на лету", не когда код уже "вылит" в продакшен.
- Если тесты упали, CI сообщает об ошибке, и разработчик сразу исправляет.

> *Пример: "Разработчик пушит в Git, CI-сервер подхватывает изменения, запускает тесты. Если всё ок, даёт зелёный свет."*

### Что такое Continuous Delivery / Deployment (CD)

**Continuous Delivery**

- Код после тестов "готов к релизу" – но финальное решение нажимает человек (менеджер, DevOps).
- Например, DevOps жмёт кнопку "Deploy to Production", зная, что все тесты пройдены.

**Continuous Deployment**

- Идём ещё дальше: если тесты и проверки прошли, код автоматически уходит в продакшен без ручного подтверждения.
- Подходит, если у вас очень частые релизы, сильное покрытие тестами и возможность быстро откатить.

> *Пример: "В интернет-магазине хотят выпускать обновления несколько раз в день. При непрерывном деплее всё делается автоматически, лишь бы тесты были зелёные."*

### Проблема, которую решил CI/CD

Раньше каждый релиз проходил примерно так:

1. Разработчик заканчивает работу → копирует файлы на сервер вручную.
2. Кто-то запускает тесты "руками" или вообще забывает их запустить.
3. Если всё ок, всё же релизим... Если нет, приходится откатывать (тоже вручную).

Это долго, утомительно и высок риск человеческих ошибок: "Ой, я забыл поставить зависимость!" или "Почему у нас разные версии пакетов?".

**CI/CD** автоматизирует сборку кода, запуск тестов, упаковку, деплой, делая релизы более быстрыми и стабильными.

```bash
CI/CD PIPELINE
Commit → Build & Test → Package → Deploy
```

### Что DevOps делает в CI/CD

| Действие | Описание |
| ---------- | ---------- |
| **Пишет пайплайн** | В Jenkins — Jenkinsfile, в GitLab — .gitlab-ci.yml, в GitHub Actions — .yaml файлы. |
| **Автоматизирует тестирование** | Юнит-тесты, интеграционные тесты, линтеры, security-сканы. |
| **Настраивает окружения** | dev → test → stage → prod. На каждом этапе свои проверки. |
| **Деплоит** | Запуск Docker-контейнеров, выкладка в Kubernetes, копирование артефактов. |

### Пример процесса CI/CD

1. **Commit**: разработчик пушит код в репозиторий (Git).
2. **Сборка (build)**: CI-сервер подхватывает код, устанавливает зависимости, компилирует/собирает.
3. **Тесты**: прогон юнит-тестов, интеграционных тестов, статических анализаторов (SonarQube, ESLint и т.п.).
4. **Сборка Docker-образа** (если требуется) и загрузка его в registry.
5. **Деплой**: на тестовое окружение (stage) или сразу на продакшен (Continuous Deployment).
6. **Мониторинг**: после заливки DevOps смотрит, всё ли ок (метрики, логи).

> *Если что-то пошло не так, можно откатиться к предыдущей версии.*

### Инструменты CI/CD

| Инструмент | Описание |
| ------------ | ---------- |
| **Jenkins** | Старожил на рынке CI/CD. Очень гибкий, но часто требует тонкой настройки. |
| **GitLab CI** | Встроена в GitLab — удобно для команд, у которых хранение кода и CI в одном месте. |
| **GitHub Actions** | Встроена в GitHub. |
| **TeamCity, CircleCI, Travis CI** | Множество вариантов, выбор зависит от конкретной компании. |

> *В России популярны Jenkins и GitLab CI (On-Premise), потому что они хорошо работают в закрытых контурах.*

### Почему без CI/CD никуда

| Преимущество | Описание |
| -------------- | ---------- |
| **Скорость релизов** | Раньше релизили раз в месяц, теперь можно хоть несколько раз в день. |
| **Стабильность** | Если что-то сломалось, CI/CD быстро покажет, где именно упали тесты или сборка. |
| **Меньше ручных ошибок** | Не нужно копировать файлы вручную, забывать вводить команды — машина всё делает сама. |

## 🏗️ IaC: Infrastructure as Code

### Проблема, которую решает IaC

Раньше, чтобы развернуть 10 серверов, инженеры заходили на каждый по SSH, ставили пакеты, правили конфиги вручную. Это:

1. **Долго**: каждый сервер настраиваем "по списку" — легко забыть или пропустить шаг.
2. **Не повторяемо**: если завтра надо добавить ещё 5 серверов, всё делаем заново, риск ошибок повышается.
3. **Сложно обновлять**: когда хочешь поменять настройку, нужно помнить, где и как уже всё прописали.

**IaC** (Infrastructure as Code) говорит: *"Давайте опишем все настройки в виде кода (файлов), а потом машина сама развёртывает, настраивает и поддерживает нужное состояние."*

### Как это устроено

1. **Файлы конфигурации**
   - Пишем сценарии для серверов: *"Создай VM, поставь Docker, открой 80-й порт."*
   - Храним их вместе с остальным кодом в Git-репозитории.

2. **Автоматическое применение**
   - Запускаем инструмент (Terraform, Ansible), который читает файл, сопоставляет, что уже есть, и **добавляет/изменяет/удаляет** ресурсы.
   - Не нужно "тыкать" руками в облаке или копировать пакеты по SSH.

3. **Версионирование**
   - Все изменения инфраструктуры идут через коммиты: *"Добавили порт 443" → есть история, кто и когда поменял."*
   - Если ошибка, можно откатиться.  

```bash
IaC: Инфраструктура описанная в коде
.tf, .yml файлы → Git version control → Автоматическое применение → Cloud/On-Premise
```

### Примеры инструментов IaC

| Инструмент | Описание |
| ------------ | ---------- |
| **Terraform** | Универсальный: описывает ресурсы (серверы, сети, базы) в облаках (Yandex, AWS, GCP) или даже VMware. Делает `plan` (показывает, что поменяется), `apply` (применяет), `destroy` (удаляет). |
| **Ansible** | Управляет настройкой ОС, пакетов, конфигов — заходит по SSH (или WinRM для Windows). Пример: "Установи Nginx, скопируй конфиг, перезапусти службу." |
| **Chef/Puppet/Salt** | Похожая идея: "все инструкции — в коде", и агенты применяют их на серверах (реже в новых проектах). |

### Зачем это DevOps

| Преимущество | Описание |
| -------------- | ---------- |
| **Повторяемость** | Хотим ещё одну тестовую среду? Запускаем те же файлы, получаем идентичную копию. |
| **Ускорение** | Нет многочасовой "ручной" настройки. Одна команда — и через минуту ресурсы готовы. |
| **Контроль версий** | Если нужно добавить порт или увеличить память, меняем пару строк в коде, commit → apply. |
| **История изменений** | Если возникла ошибка, смотрим историю, откатываем. |

### Пример: как DevOps создаёт сервер через IaC

**Ситуация:** хотим 2 виртуалки в Yandex Cloud, с Docker, чтобы запускать там контейнеры.

1. **Пишем main.tf (Terraform):**

   ```hcl
   resource "yandex_compute_instance" "app_server" {
     count = 2
     name = "app-${count.index}"
     # остальные поля: зона, образ, метаданные
   }
   ```

2. **Запускаем**

    ```bash
    terraform init    # подгрузить модули
    terraform plan    # показать, что будет создано
    terraform apply   # согласиться, и Terraform создаст 2 ВМ
    ```

3. **Получаем 2 сервера, затем (при необходимости) Ansible заходит и настраивает Docker, конфиг.**

    Без IaC всё это делалось бы вручную в интерфейсе Яндекс.Облака, и высок риск забыть про нужный порт.

## 🏗️ IaC: Infrastructure as Code

### Разница Terraform vs Ansible

| Инструмент | Назначение |
|------------|------------|
| **Terraform** | Создание инфраструктуры (виртуалок, сетей, балансировщиков) "из облака". |
| **Ansible** | Настройка уже существующих серверов (установка пакетов, правка конфигов). |

> Вместе они дают полный цикл: *"Сначала создаём машины (Terraform), потом конфигурируем их (Ansible)."*

### Плюсы и минусы IaC

| Плюсы | Минусы |
| ------- | -------- |
| Меньше ручных ошибок | Нужно время, чтобы разобраться с синтаксисом |
| Быстрее масштабирование | При большой инфраструктуре растёт "кодовой шум" |
| Всё задокументировано в коде | Нужна структура (модули, роли) |
| Легко поддерживать | |

## 📊 Мониторинг и логирование

### Зачем DevOps мониторинг

Раньше часто бывало так:

1. Сервис упал, и первые, кто об этом узнавали, — пользователи: *"Сайт не работает!"*
2. Затем разработчики *"на ощупь"* пытаются понять, где проблема.

**Мониторинг** (и алертинг) позволяет DevOps **заранее** увидеть, что нагрузка растёт или возникли какие-то ошибки, и починить сервис до жалоб пользователей.

### Важные термины

| Термин | Описание |
| -------- | ---------- |
| **Метрики** | Показатели производительности системы: CPU, память, дисковое пространство, количество запросов, время отклика. |
| **Алерты** | "Тревоги", которые система присылает при превышении порога (например, CPU > 80% в течение 5 минут). Можно настраивать уведомления в Telegram, почту, Slack. |
| **Дашборды** | Графики, где DevOps смотрит, как менялась нагрузка за последние сутки, неделю, месяц. Удобно замечать тренды и всплески. |

### КОМПОНЕНТЫ МОНИТОРИНГА

Метрики (CPU, память) → Мониторинг → Дашборды (визуализация) → Оповещения → Логи (события)

### Инструменты мониторинга

| Инструмент | Описание |
|------------|----------|
| **Prometheus + Grafana** | Prometheus "ходит" по приложениям и сервисам, собирает метрики. Grafana создает из них графики, даёт гибкий интерфейс для дашбордов. Самый популярный набор для DevOps. |
| **Zabbix** | Классическая система мониторинга (особенно в больших компаниях, госструктурах). Считывает метрики с Zabbix-агентов либо через протокол SNMP. |

### Логи: зачем их собирать

Когда приложение "упало", DevOps ищет причину. Логи (журналы событий) говорят, что произошло в момент сбоя. Без них сложно догадаться, была ли это ошибка в коде, превышение тайм-аута или сбой сети.

| Тип | Описание |
| ----- | ---------- |
| **Лог-файлы** | Часто лежат в `/var/log/`, либо пишутся в stdout (Docker-контейнеры). |
| **Centralized Logging** | Инструменты вроде ELK Stack собирают логи в единое место, иначе если у вас 20 серверов, логи будут раскиданы по всем серверам. |
| **Анализ** | Поиск grep по логам, поиск ключевых слов ("error", "exception"), построение статистики. |

### Инструменты логирования

| Инструмент | Описание |
| ------------ | ---------- |
| **ELK Stack** | **E**lasticsearch — "склад" для логов с быстрым поиском. **L**ogstash — собирает логи из разных источников, фильтрует, отправляет в Elastic. **K**ibana — инструмент для поиска и визуализации логов с удобным интерфейсом. |
| **Fluentd** | Альтернатива Logstash, собирает логи и отправляет в Elastic. |
| **Graylog** | Аналог ELK, используется в некоторых компаниях. |

> *Пример: "Приложение выдало 500-ю ошибку. В логах видим: "NullPointerException в таком-то методе". Значит, проблема в коде."*

### Пример задачи DevOps: "Настроить мониторинг + логирование"

Допустим, у нас есть приложение, работающее на нескольких контейнерах в Kubernetes.

1. **Мониторинг:**
   - Устанавливаем Prometheus + Grafana в кластер.
   - Прописываем, что наше приложение отдает метрики по пути `/metrics`.
   - Создаём дашборд в Grafana: CPU, память, число запросов, время отклика.

2. **Алерты:**
   - Если CPU > 80% более 5 минут — уведомление в Slack/Telegram.
   - Если количество ошибок (5xx) растёт, тоже алерт.

3. **Логирование:**
   - Ставим EFK (Elastic, Fluentd, Kibana) или другой стек.
   - Контейнеры пишут логи в stdout, Fluentd собирает их в Elastic.
   - В Kibana DevOps видит все логи единовременно. При ошибках легко искать "ошибка за последние 10 минут" в одном месте.

**Результат:** меньше "слепых" ситуаций. DevOps знает, что происходит с системой и быстро находит причину сбоя.

### Почему без мониторинга и логов не обойтись

| Причина | Описание |
| --------- | ---------- |
| **Предотвращение аварий** | Видим, что CPU перегружен, добавляем мощность до того, как сайт "рухнет". |
| **Быстрое расследование** | Если же всё сломалось, логи говорят, что делала программа. |
| **Улучшение планирования** | Смотрим графики, замечаем рост на 10% в месяц. Планируем ресурсы заранее. |

## 💻 Языки программирования для DevOps

### Зачем DevOps знать код

| Причина | Описание |
| --------- | ---------- |
| **Автоматизация** | DevOps пишет скрипты, соединяющие разные части инфраструктуры. |
| **Чтение чужого кода** | Нужно понимать, как собирается приложение, где лежат тесты, какие зависимости подтягиваются. |
| **Устранение мелких проблем** | Доработка скриптов сборки, Dockerfile, Terraform-плагинов на Go, Ansible-модулей на Python. |

### Какие языки нужны DevOps

| Язык | Применение |
| ------ | ------------ |
| **Bash / Shell** | Базовые скрипты в Linux: циклы, условия, работа с файлами. |
| **Python** | Очень популярен: удобен для CLI, автотестов, интеграций. Многие инструменты (Ansible) написаны на Python. |
| **Go (Golang)** | Terraform, Docker, Kubernetes написаны на Go. Понимание Go позволяет глубже кастомизировать плагины и утилиты. |
| **Чтение кода на разных языках** | Node.js, Java, C# – DevOps должен разобраться в структуре проекта и сборке (npm, Maven, MSBuild). |

> *Пример: при настройке CI/CD для Node.js нужно понимать, что `npm install` и `npm run build` делают.*

### Как DevOps учит базовую разработку

1. **Не нужно становиться крутым бэкендером**
   - Достаточно "понимать" синтаксис, структуры данных, базовые подходы к тестированию и сборке.

2. **Практические задачи**
   - Писать скрипты для развёртывания, шлифовать Dockerfile, "обшивать" Terraform/Ansible.
   - Учить Python или Bash "по ходу дела", создавая утилиты для реальных задач.

3. **Чтение чужих проектов**
   - Смотреть, как устроен build (Maven/Gradle для Java, npm/yarn для Node.js), где лежат тесты, как запускается приложение.

**Пример, когда DevOps нужен язык программирования:**

Ситуация: нужно добавить логику в CI/CD, которая проверяет Docker-образы на уязвимости, а если они старые — удаляет.

DevOps может написать небольшой Python-скрипт:

1. Получить список образов через API Docker Registry.
2. Проверить дату создания.
3. Если старше 30 дней — удалить.

Это проще и быстрее, чем делать вручную каждый раз.

## ⚠️ Типичные ошибки при изучении DevOps

| Ошибка | Почему плохо | Что делать вместо |
| -------- | -------------- | ------------------- |
| **Сразу лезть в сложные инструменты** | Без базовых знаний (Linux, сети, Docker) будет каша и фрустрация. | Начать с фундамента: Linux, сети, Docker. |
| **Бросаться во все IaC сразу** | Без понимания "зачем" будете мучиться с синтаксисом. | Взять один инструмент (Ansible или Terraform) и спокойно работать. |
| **Учить только теорию без практики** | Знания быстро забываются. | Завести пет-проект и пробовать автоматизировать. |
| **Пытаться разобраться во всём за неделю** | DevOps охватывает сети, контейнеры, CI/CD, мониторинг, логирование, безопасность. | Использовать roadmap и изучать шаг за шагом. |
| **Игнорировать soft skills** | DevOps — не только про инструменты, но и про культуру взаимодействия. | Изучать, как DevOps вписывается в процесс разработки, говорить с командой. |

**Правильный путь:**
Linux и сети → Docker и контейнеры → CI/CD и автоматизация

## 🛤️ Roadmap DevOps (Базовый уровень)

### 6 ключевых навыков для старта

| Навык | Что уметь |
| ------- | ----------- |
| **1. Linux + сети** | SSH, права, логи, порты, IP-адреса, systemd, процессы, firewall. |
| **2. Docker** | Писать Dockerfile, запускать контейнеры, использовать Docker Compose, работать с registry. |
| **3. CI/CD** | Создать простой пайплайн: сборка → тесты → деплой (Jenkins, GitLab CI). |
| **4. Облако (VPS)** | Создать виртуальную машину, открыть порт, завести домен. |
| **5. Скрипты** | Bash/Python для мелких автоматизаций. |
| **6. Мониторинг/логи** | Смотреть логи (`journalctl`, `/var/log/`) и нагрузку (`top`, `htop`). |

### Что должен уметь минимальный DevOps

1. Поднять сервер (или VPS), **задеплоить** туда приложение (через Docker или простую CI/CD).
2. Настроить **минимальный** пайплайн, чтобы при коммите код собирался и тестировался.
3. Посмотреть **логи**, починить мелкие проблемы, по SSH исправить права файлов.
4. Понимать, как открывать порты, передавать доменные имена, чтобы приложение стало доступно по "myapp.ru".

**Дальше** можно расширяться в сторону Kubernetes, Terraform, Ansible, Prometheus, Jenkins.

## 📖 Заключение

**DevOps** — это связующее звено между разработкой и эксплуатацией. Чтобы считаться DevOps (пусть на стартовом уровне) и уметь решать базовые задачи, необходимо:

1. **Linux + сети** — фундамент, на котором держится инфраструктура.
2. **Docker** — контейнеризация приложений.
3. **CI/CD** — автоматизация сборки, тестов и деплоя.
4. **IaC** — описание инфраструктуры в коде.
5. **Мониторинг и логирование** — видимость состояния системы.
6. **Языки программирования** — Bash/Python для автоматизации.

Все эти компоненты делают релизы быстрее, стабильнее и безопаснее. А DevOps-инженер становится незаменимым "смотрителем" системы, который держит всё под контролем.
