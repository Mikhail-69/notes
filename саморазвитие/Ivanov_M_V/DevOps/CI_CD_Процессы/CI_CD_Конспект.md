# CI/CD Pipeline — конспект

## 1. Что такое CI/CD в контексте SDLC

**SDLC** (Software Development Life Cycle) — это цикл разработки ПО, который включает этапы:

- разработка;
- тестирование;
- развертывание;
- сопровождение.

**CI/CD** — это подход, который автоматизирует и связывает эти этапы в единый конвейер (pipeline).  
Цель: **быстрые и надёжные релизы**.

---

## 2. CI и CD — в чём разница

| CI (Continuous Integration) | CD (Continuous Delivery / Deployment) |
|-----------------------------|----------------------------------------|
| Автоматизация **сборки, тестирования и слияния** | Автоматизация **выпуска и развертывания** |
| Запускается при каждом коммите | Управляет инфраструктурой и деплоем |
| Ловит ошибки интеграции на ранней стадии | Обеспечивает возможность выпуска в любой момент |
| Даёт быструю обратную связь разработчику | Может включать ручное утверждение (approval) перед продакшеном |

---

## 3. Стандартный CI/CD Pipeline (по шагам)
1. Коммит кода в Git  
↓  
2. CI-сервер обнаруживает изменения  
↓  
3. Сборка (компиляция, линтеры, проверки)  
↓  
4. Запуск тестов (модульные, интеграционные, e2e)  
↓   
5. Результаты → разработчику (успех / ошибка)  
↓   
6. При успехе → сборка артефактов (jar, docker-образ, etc.)  
↓  
7. Развертывание в staging-среду  
↓  
8. Дополнительные тесты на staging (нагрузочные, регрессионные)  
↓   
9. Одобрение (manual gate) → развертывание в продакшен  

---

## 4. Что даёт CI/CD команде

| Что | Зачем |
|-----|-------|
| **Автоматизация** | Убирает рутину, снижает человеческий фактор |
| **Раннее обнаружение ошибок** | Тесты запускаются на каждом коммите |
| **Быстрая обратная связь** | Разработчик знает о проблеме в течение минут |
| **Предсказуемые релизы** | Каждый релиз проходит один и тот же путь |
| **Снижение рисков** | Ошибки ловятся до продакшена |
| **Ускорение вывода фич** | Можно выпускать чаще и увереннее |

## 5. Добавлю от себя (полезные дополнения)

### 5.1. Типичные инструменты в пайплайне

| Этап | Инструменты |
|------|-------------|
| Хранение кода | GitHub, GitLab, Bitbucket |
| CI-сервер | Jenkins, GitLab CI, GitHub Actions, CircleCI, TeamCity |
| Сборка | Maven, Gradle, Webpack, Vite, Go build |
| Тестирование | JUnit, PyTest, Selenium, Playwright, Jest |
| Контейнеризация | Docker, Podman |
| Сканирование безопасности | Snyk, Trivy, SonarQube, OWASP Dependency Check |
| Развертывание | Kubernetes, Helm, Ansible, Terraform, AWS CodeDeploy |

### 5.2. Лучшие практики

- **Держи пайплайн быстрым** — долгие сборки убивают продуктивность. Параллелизируй тесты.
- **Запускай сначала быстрые тесты** (модульные), а потом долгие (e2e).
- **Используй кеширование** зависимостей — экономит время.
- **Артефакты собирай один раз** и используй на всех этапах (staging → production).
- **Не деплой в пятницу вечером** — даже с CI/CD.
- **Веди логи и метрики** пайплайна — чтобы видеть узкие места.
- **Внедри проверки безопасности** (SAST/DAST) в пайплайн, а не только тесты функциональности.

### 5.3. Термины, которые стоит знать

| Термин | Что значит |
|--------|------------|
| **Pipeline** | Последовательность шагов от коммита до продакшена |
| **Stage** | Логическая группа шагов (Build, Test, Deploy) |
| **Job** | Отдельная задача внутри stage |
| **Artifact** | Результат сборки (jar, docker image, zip) |
| **Trigger** | Событие, запускающее пайплайн (push, PR, schedule) |
| **Manual gate** | Этап, требующий ручного подтверждения (например, деплой в прод) |
| **Rollback** | Откат к предыдущей стабильной версии |
| **Blue/Green Deployment** | Стратегия развертывания с двумя средами для минимизации простоя |
| **Canary Release** | Постепенный rollout на часть пользователей |

### 5.4. Ошибки новичков в CI/CD

- ❌ Слишком много тестов на каждом коммите → пайплайн идёт 40 минут
- ❌ Игнорирование неудачных тестов («потом починим») → накапливается техдолг
- ❌ Деплой без возможности отката
- ❌ Хранение секретов в коде (пароли, токены) → используй секреты CI-системы
- ❌ Пайплайн только для продакшена, но не для dev/staging сред
- ❌ Отсутствие мониторинга после деплоя (успешный деплой ≠ всё работает)

### 5.5. Простые метрики для оценки CI/CD

- **Lead Time** — время от коммита до продакшена
- **Deploy Frequency** — как часто выпускаете релизы
- **Mean Time to Recovery (MTTR)** — среднее время восстановления после сбоя
- **Change Failure Rate** — процент релизов, которые вызвали проблемы
