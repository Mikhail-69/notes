# Семантическое Версионирование 2.0.0 — конспект

## Суть

Версия имеет формат **MAJOR.MINOR.PATCH** (например, `1.4.3`).

Увеличиваем:

- **MAJOR** — при несовместимых изменениях в публичном API;
- **MINOR** — при добавлении функциональности обратно совместимым образом;
- **PATCH** — при обратно совместимых исправлениях багов.

Дополнительно: **пре-релиз** и **сборочная метаинформация** (как расширения).

---

## Проблема, которую решает SemVer

Без чёткого управления версиями рано или поздно наступает **«ад зависимостей»**:

- **Version lock** — нельзя обновить пакет, не обновляя все зависимые от него;
- **Version promiscuity** — слишком широкие ограничения приводят к несовместимости.

SemVer даёт правила, которые позволяют понять, что изменилось в коде, просто взглянув на номер версии.

---

## Основные правила

### 1. Публичное API

Программное обеспечение, использующее SemVer, **ОБЯЗАНО** объявить публичное API. Оно должно быть:

- точным;
- полным;
- описанным в коде или документации.

### 2. Формат номера версии

- Формат: `X.Y.Z`, где `X`, `Y`, `Z` — **неотрицательные целые числа**.
- **Без ведущих нулей** (нельзя `01.0.0`).
- Каждый элемент увеличивается численно: `1.9.0` → `1.10.0` → `1.11.0`.

### 3. Неизменность релизов

После того как версия выпущена — **её содержимое НЕЛЬЗЯ менять**. Любые изменения — только как новая версия.

### 4. Версия 0.y.z

`0.y.z` — для начальной разработки. Всё может меняться в любой момент. Публичное API **НЕ СЧИТАЕТСЯ** стабильным.

### 5. Версия 1.0.0

`1.0.0` — это точка, когда публичное API объявлено стабильным. Дальнейшие изменения версии зависят от того, как меняется API.

---

## Когда увеличивать

| Версия | Когда увеличивать |
|--------|-------------------|
| **PATCH** (`x.y.Z`) | Только обратно совместимые **исправления багов** |
| **MINOR** (`x.Y.z`) | Добавлена **новая функциональность** обратно совместимым образом; или часть API **объявлена устаревшей** (deprecated). Может содержать изменения уровня PATCH. При увеличении MINOR, PATCH сбрасывается в `0`. |
| **MAJOR** (`X.y.z`) | Любые **несовместимые изменения** в публичном API. Может содержать изменения уровня MINOR и PATCH. При увеличении MAJOR, MINOR и PATCH сбрасываются в `0`. |

## Пре-релизы

Обозначаются **дефисом** и идентификаторами через точку сразу после номера патча:  
1.0.0-alpha  
1.0.0-alpha.1  
1.0.0-0.3.7   


**Правила:**
- идентификаторы только из `[0-9A-Za-z-]`;
- числовые идентификаторы **без ведущих нулей**;
- пре-релиз имеет **меньший приоритет**, чем обычная версия.

---

## Сборочная метаинформация (build metadata)

Обозначается **плюсом** и идентификаторами через точку после патча или пре-релиза:   
1.0.0+20130313144700   
1.0.0-alpha+001  
1.0.0+21AF26D3


**Правила:**
- идентификаторы только из `[0-9A-Za-z-]`;
- **игнорируется** при определении приоритета версий.

---

## Приоритет версий (сравнение)

Сравнение происходит по частям: **MAJOR → MINOR → PATCH → пре-релиз**.

1. MAJOR, MINOR и PATCH сравниваются **численно**:  
1.0.0 < 2.0.0 < 2.1.0 < 2.1.1

2. Если MAJOR, MINOR, PATCH равны — **пре-релиз имеет меньший приоритет**, чем обычная версия:  
1.0.0-alpha < 1.0.0


3. Сравнение двух пре-релизов:
- числовые идентификаторы сравниваются **численно**;
- буквенные и с дефисом — **лексикографически** (по ASCII);
- числовые идентификаторы всегда **ниже** нечисловых;
- больше полей → выше приоритет, если все предыдущие равны.

**Пример:**  
1.0.0-alpha <  
1.0.0-alpha.1 <  
1.0.0-alpha.beta <  
1.0.0-beta <  
1.0.0-beta.2 <  
1.0.0-beta.11 <  
1.0.0-rc.1 <  
1.0.0

## Зачем использовать SemVer

- Позволяет **понять намерения автора** по номеру версии.
- Даёт возможность указывать зависимости **гибко, но безопасно** (например, `>= 3.1.0 < 4.0.0`).
- Избавляет от «ада зависимостей».
- Экономит время разработчиков.

## Важные моменты из FAQ

| Вопрос | Ответ |
|--------|-------|
| Как быть с `0.y.z`? | Начинайте с `0.1.0`, увеличивайте MINOR при каждом релизе |
| Когда выпускать `1.0.0`? | Если софт в продакшене или есть стабильное API — уже пора |
| Не приведёт ли это к версии `42.0.0`? | Это заставляет ответственно подходить к изменениям и оценивать их стоимость |
| Документировать всё API — слишком много работы | Это ответственность профессионала. Без документации никто не сможет использовать ваш софт |
| Случайно выпустил ломающее изменение как MINOR? | Сразу выпусти новую MINOR-версию с исправлением. Не изменяй уже выпущенный релиз |
| Обновил зависимости — что делать? | Если публичное API не изменилось — версия не меняется или меняется PATCH/MINOR в зависимости от характера обновления |
| Как обрабатывать deprecated? | Сделай MINOR-релиз с пометкой устаревания, затем MAJOR — с удалением |
| Есть ли ограничение на длину версии? | Нет, но 255 символов — явный перебор |
| Является ли `v1.2.3` семантической версией? | Нет. Это тег с префиксом `v`. Сама версия — `1.2.3` |

## Регулярные выражения для проверки SemVer

### С именованными группами (PCRE, Python, Go)

```regex
^(?P<major>0|[1-9]\d*)\.(?P<minor>0|[1-9]\d*)\.(?P<patch>0|[1-9]\d*)(?:-(?P<prerelease>(?:0|[1-9]\d*|\d*[a-zA-Z-][0-9a-zA-Z-]*)(?:\.(?:0|[1-9]\d*|\d*[a-zA-Z-][0-9a-zA-Z-]*))*))?(?:\+(?P<buildmetadata>[0-9a-zA-Z-]+(?:\.[0-9a-zA-Z-]+)*))?$
```
### С нумерованными группами (JavaScript, PCRE, Python, Go)

```regex
^(0|[1-9]\d*)\.(0|[1-9]\d*)\.(0|[1-9]\d*)(?:-((?:0|[1-9]\d*|\d*[a-zA-Z-][0-9a-zA-Z-]*)(?:\.(?:0|[1-9]\d*|\d*[a-zA-Z-][0-9a-zA-Z-]*))*))?(?:\+([0-9a-zA-Z-]+(?:\.[0-9a-zA-Z-]+)*))?$
```
